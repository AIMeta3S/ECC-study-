# ECC 安装过程分析（学习笔记）

> 本文档整理了对 ECC（Everything Claude Code）三种安装相关问题的深入分析，全部基于对 [install.sh](../install.sh)、[scripts/install-apply.js](../scripts/install-apply.js)、[manifests/](../manifests/)、[.claude-plugin/](../.claude-plugin/) 等源码的静态阅读与 dry-run 验证得出。
>
> 分析时的仓库版本：v2.0.0，默认 `--target claude`，安装根 = `~/.claude/`。

---

## 问题一：纯手动安装（`./install.sh --profile full`）执行了哪些操作？

### 问题
分析"纯手动安装"时，安装脚本对电脑环境做了哪些改变：
1. 创建了哪些文件和文件夹？
2. 修改了哪些内容（文件、文件夹、配置、环境变量）？
3. 罗列对电脑环境所有的改变。

### 结论先行
`./install.sh --profile full` 是**纯文件复制式安装**：只往 `~/.claude/` 下写新文件，**不修改任何已有配置**——`settings.json`、`.mcp.json`、`CLAUDE.md`、shell 配置、环境变量一律不动（全链路 grep 不到 `settings.json`，且 claude target 的 adapter 只生成 `copy-path` 操作，从不生成 `merge-json`）。

### 执行链路
[install.sh](../install.sh) →（首次运行先 `npm install` 装依赖到仓库）→ `node [install-apply.js](../scripts/install-apply.js)` → `createManifestInstallPlan`（[install-executor.js:691](../scripts/lib/install-executor.js#L691)）→ `applyInstallPlan`（[install/apply.js:118](../scripts/lib/install/apply.js#L118)）。

默认 `--target claude`，安装根 = `~/.claude/`，状态文件 = `~/.claude/ecc/install-state.json`（[claude-home.js:49-54](../scripts/lib/install-targets/claude-home.js#L49)）。

`full` profile 展开为 **22 个 module**（[install-profiles.json:73](../manifests/install-profiles.json#L73)），每个 module 声明一组源路径（[install-modules.json](../manifests/install-modules.json)），由 claude-home adapter 按下表规则映射到目标。

### 路径映射规则（target=claude）

| 源路径（仓库内） | 目标位置 | 说明 |
|---|---|---|
| `rules/`、`rules/*` | `~/.claude/rules/ecc/...` | 重映射到 `ecc/` 子目录（路径隔离，非命令前缀） |
| `skills/`、`skills/*` | `~/.claude/skills/ecc/...` | ⚠️ 重映射到 `ecc/` 子目录，但 **Claude Code 不扫描此层，skill 装了也无法识别**（详见下方警告） |
| `.claude-plugin/`（native root） | `~/.claude/`（**提升到根**） | `plugin.json`、`marketplace.json` 直接放根目录 |
| `agents`、`commands`、`hooks`、`scripts/*`、`mcp-configs`、`AGENTS.md`、`the-security-guide.md` 等 | `~/.claude/<原相对路径>` | 原样拼接 |
| `.codex`、`.cursor`、`.gemini`、`.opencode`、`.qwen`、`.zed`、`.codebuddy`、`.joycode` | **跳过** | 属其它平台，`isForeignPlatformPath` 过滤 |
| `docs/*` | `~/.claude/docs/...` | 仅 `--locale` 时启用，full 不含 |

### 一、新建的目录与文件（全部在 `~/.claude/` 下）

- **`rules/ecc/`** — 整个 `rules/` 递归复制（含 `common`、`typescript`、`python`、`golang`、`swift`、`php`、`node` 等）。来自 `rules-core`。
- **`skills/ecc/`** — **198 个 skill 目录（展开为 305 个文件）**（full profile 按 module 精选；仓库共 277 个，另有 **79 个未被任何 install module 收录**，install.sh 任何参数都装不到）。来自多个 skill 类 module。⚠️ **此位置 Claude Code 不识别，skill 装了也无法使用**，详见下方警告。
- **`agents/`** — 全量 agents（约 67 个 `.md`）。来自 `agents-core`。
- **`.agents/`** — 仓库的 `.agents/` 目录内容，其中 **`.agents/skills/`（core skills，84 文件）落到 `~/.claude/.agents/skills/`**——既不在 `skills/ecc/` 也不在扁平 `skills/`，⚠️ **Claude Code 同样不识别**。
- **`commands/`** — 全量斜杠命令（约 92 个 `.md`）。来自 `commands-core`。
- **`hooks/`** — 含 `hooks.json` 及子目录。来自 `hooks-runtime`。
- **`scripts/`** — 含 `scripts/lib/`（整个工具库）、`scripts/hooks/`、以及 `harness-audit.js`、`skills-health.js`、`auto-update.js`、`setup-package-manager.js`、`claw.js`、`orchestrate-*.js/.sh`、`tmux-worktree-orchestrator.js` 等。
- **`mcp-configs/`** — `mcp-servers.json`（MCP 服务目录，**仅复制，不激活**）。
- **顶层散文件（6 个）**：`~/.claude/AGENTS.md`、`~/.claude/the-security-guide.md`，以及 `.claude-plugin/` 全部 4 个文件提升到根——`plugin.json`、`marketplace.json`、`README.md`、`PLUGIN_SCHEMA_NOTES.md`。
- **`ecc/install-state.json`** — 安装状态记录（profile、selectedModules、repoVersion、repoCommit、完整 operations 清单）。由 [install-state.js:301](../scripts/lib/install-state.js#L301) 写入。

> ### ⚠️ 重要：install.sh 装的 skill 无法直接使用
>
> Claude Code 只从 `~/.claude/skills/` 的**直接子目录**（一层 `<name>/SKILL.md`）发现 skill，**不递归**。`install.sh --profile full` 却把 skill 放到 `~/.claude/skills/ecc/<name>/`（多一层 `ecc/`），导致 **Claude Code 不扫描此层，全部 skill 失效**。
>
> 这是 ECC 官方文档明确警告的：
> - [README.md:974](../README.md#L974)：`Do not nest manual installs under ~/.claude/skills/ecc/.`
> - [docs/de-DE/README.md:902](../docs/de-DE/README.md#L902)：Claude Code 只从 `~/.claude/skills/` 的**直接子目录**加载 skill。
> - [configure-ecc 手动示例](../docs/zh-CN/skills/configure-ecc/SKILL.md#L23) 路径是扁平的 `~/.claude/skills/configure-ecc/SKILL.md`。
>
> `ecc/` 命名空间是为 **plugin 形态**设计的（plugin 下 `skills/ecc/<name>/` 合法，命名空间 `ecc:<name>`），单独手动安装到 `~/.claude/skills/` 时不适用。
>
> **正确做法（手动安装 skill）—— 扁平复制：**
>
> ```bash
> mkdir -p ~/.claude/skills
> cp -r skills/search-first ~/.claude/skills/   # 想要哪个就 cp 哪个，目标无 ecc/
> ```
>
> 扁平安装后（`~/.claude/skills/<name>/SKILL.md`），skill 的触发方式：
> - **自动触发**（最常见）：Claude 按 SKILL.md frontmatter 的 `description` 判断相关性自动加载。
> - **显式触发**：`/<目录名>`，例如 `/search-first`。**skill 名 = 目录名**，不是 frontmatter 的 `name` 字段（`name` 仅作显示标签）。
>
> **结论**：`install.sh --profile full` 适合装 rules/agents/commands/hooks，**skill 不要用它装**——改用扁平 `cp -r`，或用插件方式 `/plugin install ecc@ecc`。

量级：端到端 dry-run 实测共 **836 个文件操作**（`node install-apply.js --profile full --dry-run`）。

### 二、修改（覆盖）的内容

1. **`~/.claude/hooks/hooks.json`**：apply 阶段会读取它，把 `${CLAUDE_PLUGIN_ROOT}` 占位符替换成 `~/.claude/`（[apply.js:91-116](../scripts/lib/install/apply.js#L91)），再写回。这样 hook 命令里的脚本路径会指向 `~/.claude/scripts/hooks/*.js`。
2. **任何同名已存在文件会被覆盖**：复制用 `fs.copyFileSync`（[apply.js:152](../scripts/lib/install/apply.js#L152)），目录用 `mkdirSync recursive` + 逐文件覆盖。

### 三、仓库目录内的副作用
- **首次运行**会在仓库 `/Users/liuxw/githubProject/ECC-study-/` 下创建 `node_modules/`（[install.sh:18-21](../install.sh#L18)，`npm install --no-audit --no-fund`），用于装 `ajv` 等依赖。这只影响仓库本身，不影响 `~/.claude/`。

### 四、明确【不会】改变的内容（重要否定清单）

| 项目 | 是否改动 |
|---|---|
| `~/.claude/settings.json` | ❌ 不动 |
| `~/.claude/.mcp.json` | ❌ 不创建/不合并（MCP 需手动配置） |
| `~/.claude/CLAUDE.md` | ❌ 不动 |
| shell 配置（`.zshrc`/`.bash_profile` 等） | ❌ 不动 |
| 环境变量 | ❌ 不设置任何变量 |
| 其它平台目录（`.codex`/`.cursor` 等） | ❌ target=claude 时全部跳过 |
| Claude Code 本体 | ❌ 不触碰 |

### 五、特别提醒
1. **不要与 `/plugin install ecc@ecc` 叠加**。[README.zh-CN.md:116-120](../README.zh-CN.md#L116) 明确警告：插件已自动加载 skills/commands/hooks，再跑 `install.sh --profile full` 会把同一批内容复制到用户目录，导致技能重复、hook 重复执行。
2. **MCP 不会自动启用**。需自己把 `mcp-configs/mcp-servers.json` 里的条目粘进 `~/.claude/settings.json` 或项目 `.mcp.json`，并填入真实 API key。
3. **卸载**：ECC 提供了 [uninstall.js](../scripts/uninstall.js)，可读 `~/.claude/ecc/install-state.json` 回滚它写入的内容。

### 六、如何自己验证完整清单
```bash
# 装好仓库依赖后，跑只读 dry-run 可拿到逐文件的完整 plan，不写任何东西
node scripts/install-apply.js --profile full --dry-run --json | jq '.plan.operations[] | {src: .sourceRelativePath, dst: .destinationPath}'
```

## 问题二：`/plugin install ecc@ecc` 与纯手动安装的区别

### 问题
从安装内容、使用方式等方面对比两种安装方式。

### 关键背景
[plugin.json](../.claude-plugin/plugin.json) **只声明 `skills` 和 `commands`**，`agents` 和 `hooks` 都按约定自动发现（[PLUGIN_SCHEMA_NOTES.md:58-75, 98-133](../.claude-plugin/PLUGIN_SCHEMA_NOTES.md#L58)）；而 [hooks.json](../hooks/hooks.json) 里的 hook 命令自带 `CLAUDE_PLUGIN_ROOT` 环境变量 + 路径 fallback 解析，是**为两种安装方式共同设计的**。

### 一、安装机制：谁在装、装到哪

| 维度 | `/plugin install ecc@ecc` | `./install.sh --profile full` |
|---|---|---|
| 本质 | Claude Code 拉取 marketplace 仓库到**插件缓存**并引用 | **物理复制**文件到用户目录 |
| 安装位置 | `~/.claude/plugins/...`（Claude Code 托管） | 散落到 `~/.claude/` 各子目录 |
| 内容来源 | 整仓引用，由 `plugin.json` 声明暴露面 | 按 profile/module **精选**复制 |
| 依赖安装 | 不需要 | 首次跑会 `npm install`（装 `ajv` 等到仓库 `node_modules/`） |
| 启用记录 | 写 `~/.claude/settings.json` 的 `enabledPlugins` / `extraKnownMarketplaces` | 写 `~/.claude/ecc/install-state.json`（不动 `settings.json`） |

### 二、安装内容：组件级逐项对比

| 组件 | 插件方式 | 手动方式 | 说明 |
|---|---|---|---|
| **skills** | 全量 **277** 个，`ecc` 命名空间 | `full` profile 约 **194** 个（精选子集，放 `~/.claude/skills/ecc/`） | 手动是精选子集，未纳入任何 module 的 skill 不装 |
| **commands** | 全量 **92**，`/ecc:xxx` 命名空间 | 全量 92，`/xxx` **无命名空间** | 命令调用形式不同 |
| **agents** | 全量 **67**（约定自动发现，不可在 manifest 声明） | 全量 67，复制到 `~/.claude/agents/` 全局 | 插件 manifest 禁止 `agents` 字段（验证器报错） |
| **hooks** | 自动加载 `hooks/hooks.json`，`CLAUDE_PLUGIN_ROOT` 由 Claude Code 注入 | 复制到 `~/.claude/hooks/hooks.json`，apply 时占位符替换为 `~/.claude/` | 同一份 hooks.json，两种解析路径 |
| **rules** | ❌ **不支持**（Claude Code 插件系统限制，无法分发） | ✅ 复制到 `~/.claude/rules/ecc/`（含 common + 各语言） | 插件用户必须额外手动复制 `rules/` |
| **MCP** | ❌ 显式 opt-out（`mcpServers: {}`，防工具名超 64 字符） | 复制 `mcp-configs/mcp-servers.json`（仅复制不激活） | 两种方式都需用户手动配 key |
| **scripts/lib 等** | 不装（hook 运行时从插件缓存根解析） | 复制到 `~/.claude/scripts/`（hook 依赖的运行时脚本） | 手动方式需自带脚本依赖 |
| **顶层文件** | 无 | `AGENTS.md`、`plugin.json`、`marketplace.json`、`the-security-guide.md` 提升到 `~/.claude/` 根 | |

### 三、使用方式区别
1. **命令调用**：插件用 `/ecc:plan "需求"`，手动用 `/plan "需求"`（[README.zh-CN.md:156-164](../README.zh-CN.md#L156)）。
2. **rules 缺失补救**：插件方式若想生效规则，需手动 `cp -R rules/common ~/.claude/rules/` 等。
3. **skill 触发范围**：插件 skills 在 `ecc` 命名空间下隔离；手动 skills 在全局 `~/.claude/skills/ecc/`，与用户已有 skill 共存。
4. **`multi-*` 命令**：两种方式都**不包含** `ccg-workflow` 运行时，需额外 `npx ccg-workflow` 初始化（[README.zh-CN.md:169-181](../README.zh-CN.md#L169)）。

### 四、更新、卸载、版本管理

| 操作 | 插件方式 | 手动方式 |
|---|---|---|
| 更新 | `/plugin marketplace update ecc` → `/plugin update` | `git pull` → 重跑 `./install.sh --profile full` |
| 卸载 | `/plugin uninstall ecc@ecc`（干净） | 跑 [uninstall.js](../scripts/uninstall.js)，读 `install-state.json` 回滚 |
| 版本锁定 | 由 marketplace 管理 | 由本地 git commit 决定，可控 |

### 五、选择性与定制能力（手动方式的优势）
- 插件方式：**只能整体启用/禁用**，277 个 skill 全量加载，无法挑选。
- 手动方式：支持 `--profile minimal|core|developer|research|security|full`、`--modules <id,...>`、`--skills <id,...>`、`--with/--without <component>` 精细裁剪（[install-apply.js:46-58](../scripts/install-apply.js#L46)）。

### 六、跨 harness 支持（手动方式的另一优势）
插件方式是 **Claude Code 专属**。手动方式支持 `--target cursor|codex|gemini|opencode|zed|codebuddy|joycode|qwen|antigravity`，可同时给多个 AI 工具铺配置。

### 七、关键警告：两种方式不可叠加
插件已自动加载 skills/commands/hooks，**再跑 `install.sh --profile full` 会把同一批内容复制到用户目录**，导致：
- skill 重名重复触发
- hook 重复执行（同一事件跑两遍）
- `${CLAUDE_PLUGIN_ROOT}` 解析冲突

**二选一。**

### 八、怎么选
- **选插件**：只用 Claude Code、想要最省事、需要全量 277 skill、不在意 rules 自动分发。**记得额外手动补 `rules/`**。
- **选手动**：需要 rules 生效、想要精选安装（轻量）、要跨多个 harness、或想锁定特定 commit。

**一句话**：插件 = 全量 + 命名空间隔离 + 无 rules + 托管；手动 = 可精选 + 全局生效 + 含 rules + 自管。两者都自动激活 hooks、都不自动配 MCP、都不能省 `ccg-workflow`。

## 问题三：手动安装时为什么要先 `npm install`？

### 问题
`npm install` 是为了给安装过程提供保障，还是使用 ECC 的时候提供保障？

### 直接回答：**是为安装过程提供保障**
`npm install` 装的 3 个第三方包（`ajv`、`@iarna/toml`、`sql.js`），核心被安装链路硬依赖；而日常使用 ECC 时触发的 hooks **零第三方依赖**，装不装都照样跑。

### 证据：3 个包各归谁

| 包 | 安装过程用 | 使用 ECC 时用 | 性质 |
|---|---|---|---|
| `ajv` | ✅ [config.js:5](../scripts/lib/install/config.js#L5) **硬 require**，校验 `ecc-install.json` | 间接（[state-store/schema.js](../scripts/lib/state-store/schema.js#L5)，可选高级功能） | **安装硬门槛** |
| `@iarna/toml` | `--target codex` / Codex 同步时（[codex/merge-codex-config.js](../scripts/codex/merge-codex-config.js#L19)） | control-pane 读 Codex TOML（可选） | 边缘 |
| `sql.js` | ❌ | control-pane/state-store 的 SQLite 持久化（可选） | 与安装无关 |

> **实证**：直接跑 `node install-apply.js --dry-run` 会崩，报错正是 `Cannot find module 'ajv'`，require 栈起点是 `scripts/lib/install/config.js`。这就是"没装 ajv → 安装过程跑不起来"的活证据。

### 两个关键事实

**1. 日常 hooks 不依赖 npm install。** 对 `scripts/hooks/` 全量扫描，所有 `require` 都是相对路径（`../lib/utils`、`./bash-hook-dispatcher` 等）或 Node 内置模块——**没有任何一个第三方包**。PreToolUse、PostToolUse、Stop 这些每次工具调用都会触发的 hook，只靠 Node 内置模块 + 本地 `scripts/lib/utils.js`，装不装依赖完全不影响。

**2. `npm install` 装在仓库目录，不进 `~/.claude/`。** [install.sh:20](../install.sh#L20) 的 `npm install` 在仓库根（`/Users/liuxw/githubProject/ECC-study-/node_modules/`）。手动安装只把 `scripts/lib/` 等文件**复制**到 `~/.claude/scripts/lib/`，**不复制 `node_modules`**。所以即便那些需要 `sql.js`/`toml` 的可选运行时模块（state-store、control-pane）被复制过去了，`~/.claude/` 那边也找不到这些包——`npm install` 对"使用 ECC 时"在目标目录里根本帮不上忙。那些模块主要服务于**仓库内**场景（开发、CI、`npx ecc`、Codex 同步），不是手动安装后的日常 hook 链路。

### 总结
`npm install` 的真正作用是让 **installer 自己能跑起来**（`ajv` 是 `install-apply.js` 的硬前置），附带也让仓库内的开发/CI/Codex 同步脚本可用。它**不是**日常使用 ECC（hooks、skills、commands）的前提——那部分只用 Node 内置模块。
