# Research Ops

当用户要求研究某个当前话题、对比多个选项、对人员或公司信息进行补充，或将重复查询转为受监控的工作流时，使用本 skill。

这是围绕本仓库研究栈（research stack）的调度封装层。它并不替代 `deep-research`、`exa-search` 或 `market-research`，而是告诉你何时以及如何将它们组合使用。

## Skill 栈

在相关场景下，将以下 ECC 原生 skill 纳入工作流：

- `exa-search`：用于快速的当前网络发现
- `deep-research`：用于带引用的多来源综合
- `market-research`：当最终结果应当是一个推荐或排序后的决策时使用
- `lead-intelligence`：当任务面向人员/公司定向，而非通用研究时使用
- `knowledge-ops`：当结果随后应被存入持久化上下文时使用

## 何时使用

- 用户说"研究"、"查找"、"对比"、"我该联系谁"或"最新进展"
- 答案依赖于当前的公开信息
- 用户已经提供了证据，希望将其纳入一个全新的推荐中
- 任务可能足够重复，应当变成一个监控而不是一次性的查询

## 约束

- 当新搜索成本很低时，不要用过期记忆回答当前性问题
- 区分以下几类内容：
  - 有来源的事实
  - 用户提供的证据
  - 推断
  - 推荐
- 如果答案已在本地代码或文档中，不要发起一次重量级的研究流程

## 工作流

### 1. 从用户已经给你的内容开始

将任何已提供的材料归整为：

- 已有证据支持的事实
- 需要验证的内容
- 开放性问题

如果用户已经构建了模型的一部分，不要从零开始重新分析。

### 2. 对请求进行分类

在搜索前选择正确的通道：

- 快速的事实性回答
- 对比或决策备忘
- 线索/补充流程
- 周期性监控候选

### 3. 优先采用最轻量且足够的证据路径

- 使用 `exa-search` 进行快速发现
- 当综合或多来源很重要时，升级到 `deep-research`
- 当结果应当以一个推荐收尾时，使用 `market-research`
- 当真正的诉求是目标排序或暖路径发现（warm-path discovery）时，移交给 `lead-intelligence`

### 4. 报告时显式标注证据边界

对于重要的断言，说明它们属于：

- 有来源的事实
- 用户提供的上下文
- 推断
- 推荐

对时效性敏感的回答应包含具体日期。

### 5. 判断该任务是否应保持手工执行

如果用户可能反复提出同一研究问题，请明确指出，并推荐一个监控层或工作流层，而不是永远重复同一手工搜索。

## 输出格式

```text
问题类型
- 事实性 / 对比 / 补充 / 监控

证据
- 有来源的事实
- 用户提供的上下文

推断
- 由证据推出的内容

推荐
- 回答或下一步动作
- 是否应转为监控
```

## 陷阱

- 不要在未标注的情况下，把推断混入有来源的事实
- 不要忽略用户提供的证据
- 不要为本地仓库上下文就能回答的问题，启用重型研究通道
- 对时效性敏感的回答不要遗漏日期

## 验证

- 重要的断言已按证据类型标注
- 对时效性敏感的输出包含日期
- 最终的推荐与实际使用的研究模式相匹配
