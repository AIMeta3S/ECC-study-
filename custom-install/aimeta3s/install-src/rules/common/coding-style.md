# 编码风格

## 不可变性 (CRITICAL)

**始终**创建新对象，**绝不**修改已有对象：

```
// 伪代码
错误：  modify(original, field, value) → 直接修改 original
正确：  update(original, field, value) → 返回带修改的新副本
```

理由：不可变数据能防止隐藏的副作用，让 debug 更容易，并支持安全的并发。

## 核心原则

### KISS (Keep It Simple)

- 优先选择最简单有效的解决方案。
- 避免过早优化
- 注重清晰度而非技巧性。

### DRY (Don't Repeat Yourself)

- 将重复逻辑抽取为共享函数或工具
- 避免复制粘贴导致的实现差异
- 当重复确实存在而非推测时，才引入抽象

### YAGNI (You Aren't Gonna Need It)

- 不要在需要之前构建功能或抽象
- 避免臆测性的通用设计
- 从简单开始，等压力确实出现时再重构

## 文件组织

多个小文件 > 少数大文件：
- 高内聚，低耦合
- 通常 200-400 行，最多 800 行
- 从大型模块中提取工具函数
- 按功能/领域组织，而非按类型组织

## 错误处理

**务必**全面妥善地处理错误：
- 在每一层都显式处理错误
- 在面向 UI-facing 的代码中提供 user-friendly 的错误信息
- 在服务器端记录详细的错误上下文
- 永远不要默默吞下错误

## 输入校验

**务必**在系统边界处进行验证：
- 在处理前校验所有用户输入
- 在可用时使用 schema-based 校验
- 快速失败，并提供清晰的错误信息
- 永远不要相信外部数据（API 响应、用户输入、文件内容）

## 命名规范

- 变量和函数：使用 `camelCase`，并使用描述性名称
- 布尔值：优先使用 `is`、`has`、`should` 或 `can` 前缀
- interface、type、components：使用 `PascalCase`
- 常量：使用 `UPPER_SNAKE_CASE`
- 自定义 hook：使用 `camelCase` 并带 `use` 前缀

## 应避免的 code smell

### 过深嵌套

一旦逻辑开始堆叠，优先使用 early return，而非嵌套的条件判断。

### Magic Number

使用命名常量来定义有意义的阈值、延迟和限制。

### Long Functions

将大型函数拆分为职责清晰、聚焦的小块。

## 代码质量检查清单

在标记工作完成之前：
- [ ] 代码可读性好，命名规范。
- [ ] function 保持小巧（<50 行）
- [ ] 文件聚焦（<800 行）
- [ ] 无过深嵌套（>4 层）
- [ ] 错误处理得当
- [ ] 无硬编码值（使用常量或配置）
- [ ] No mutation（使用不可变模式）
