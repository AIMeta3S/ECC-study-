# PRD Command

产出一份 **产品需求文档** —— SDLC 中需求阶段的产物。捕获为达成成功所必须成立的 *what* 与 *why*，并在进入 *how* 之前止步。实现层面的拆解交由 `/plan` 处理。

**输入**：`$ARGUMENTS`

## 本命令的范围

| 本命令负责 | 本命令不负责 |
|---|---|
| 界定问题和用户 | 设计架构 |
| 捕获成功标准和范围 | 选择文件或编写模式 |
| 列出未解决的问题和风险 | 枚举实现任务 |
| 写入 `.claude/prds/{name}.prd.md` | 产出实现计划——那是 `/plan` 的工作 |

如果你发现自己在写实现细节，停下来删掉它。那属于 `/plan` 的范畴。

**Anti-fluff rule**：当信息缺失时，写入 `TBD — 需通过 {方法} 验证`。绝不编造听起来合理的需求。

## 工作流

四个阶段。每个阶段都是单一门控 —— 提出问题，等待用户回答，然后继续。没有嵌套循环，也没有并行研究流程。

### Phase 1 —— FRAME

如果 `$ARGUMENTS` 为空，提问：

> 你想建造什么？一两句话概括一下。

如果已提供，用一句话复述并询问：

> 我的理解是：*{restated}*。这样理解对吗？还是需要我调整一下？

然后一次性提出以下框定问题：

> 1. **Who** 有这个问题？（具体的角色或群体）
> 2. **What** 是可观察的痛点？（描述行为，而非假定的需求）
> 3. **Why** 他们无法用现有的工具解决？
> 4. **Why now?** —— 发生了什么变化，让这件事值得做？

等待用户回答。没有答案（或明确的 "skip"）不得继续。

### Phase 2 —— GROUND

索要依据。这是最短却最关键的一个阶段：

> 你有什么依据表明这个问题真实存在且值得解决？（用户原话、客服（用户反馈）工单、数据指标、观察到的用户行为、失败的临时解决方案——任何具体的凭据）

如果用户没有依据，将 PRD 的依据部分记录为 `假设 — 需通过 {用户调研 | 分析 | 原型} 验证`。这样可以确保 PRD 的真实性。

### Phase 3 —— DECIDE

范围与假设一次性提出：

> 1. **假设** — 完成：*我们相信 **{能力}** 将为 **{用户}** 解决 **{问题}**。当我们看到 **{可衡量结果}** 时，就知道我们是对的。*
> 2. **MVP** — 验证假设所需的最小量是什么？
> 3. **不在范围内** — 你明确**不**构建什么（即使有用户要求）？
> 4. **待决问题** — 可能改变方案的不确定因素？

等待回答。

### Phase 4 —— GENERATE & HAND OFF

如有需要则创建目录，编写 PRD，并汇报。

```bash
mkdir -p .claude/prds
```

**输出路径**：`.claude/prds/{kebab-case-name}.prd.md`

#### PRD 模板

```markdown
# {产品 / 功能名称}

## 问题定义
{用2–3句话说明：目标用户遇到了什么问题，不解决会带来什么代价？}

## 需求依据
- {用户原话（例如访谈记录、工单原文、评论原句等）、数据凭据或观察发现}
- {或：“假设 — 需通过 {方法} 验证”}

## 目标用户
- **主要用户**：{角色、使用场景、需求触发条件}
- **排除对象**：{明确指出不在考虑范围内的用户}

## 假设
我们相信 **{能力}** 将为 **{用户}** 解决 **{问题}**。
当我们看到 **{可衡量结果}** 时，就知道我们是对的。

## 成功指标
| 指标 | 目标 | 衡量方式 |
|---|---|---|
| {主属性} | {数值} | {方法} |

## 范围
**MVP** — {验证假设所需的最小可行产品}

**不在范围内**
- {条目} — {推迟原因}

## 交付里程碑
<!-- 业务成果，而非工程任务。/plan 将每个转化为计划。 -->
<!-- 状态：pending | in-progress | complete -->

| # | 里程碑 | 成果 | 状态 | 计划 |
|---|---|---|---|---|
| 1 | {名称} | {用户可见变化} | pending | — |
| 2 | {名称} | {用户可见变化} | pending | — |

## 待决问题
- [ ] {可能改变范围或方案的问题}

## 风险
| 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|

---
*状态：DRAFT — 仅需求。实现规划待通过 /plan 进行。*
```

#### 向用户汇报

```
PRD 已创建：.claude/prds/{name}.prd.md

问题：    {一行}
假设：    {一行}
MVP：     {一行}

验证状态：
  问题  {已验证 | 假设}
  用户  {具体 | 泛化 — 需细化}
  指标  {已定义 | 待定}

未解决问题：{数量}

下一步：/plan .claude/prds/{name}.prd.md
  → /plan 将选取下一个待办的里程碑并产生实现计划。
```

## 衔接

- `/plan <prd-path>` — 以该 PRD 为输入，为下一个待办里程碑制定实现计划。
- `tdd-workflow` skill — 采用测试优先的方式执行该计划。
- `/pr` — 创建一个 PR，关联本 PRD 与对应的计划。

## 成功标准

- **问题清晰**：问题具体且有证据支撑（或标记为假设）。
- **用户具象**：主要用户是一个具体的角色，而非泛指的 "users"。
- **假设可验证**：包含可衡量的结果。
- **范围有界**：有明确的 MVP 和明确的 out-of-scope。
- **无实现细节**：不含文件路径、libraries 或任务拆解 —— 如果出现了，删除他们。
