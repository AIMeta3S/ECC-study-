# ECC

你的 agent 可以写代码，但 ECC 赋予它一套协同的工程化系统与工具箱：它在构建之前先做 plan，用 test 验证变更，从 fresh context 审查自己的工作，记住重要事项，并将反复取得的成功转化为可复用的 skills 和 workflows。

```text
plan -> test -> implement -> review -> verify -> remember -> improve
```

你不必在每个 prompt 中重建这个过程，只需安装一次，让它成为你 agent 工作方式的一部分。

> 优化 context window。将其余一切持久化。

ECC 是 MIT-licensed open source 软件。目前与 Claude Code 配合效果最佳，拥有一条受支持的 Codex sync 路径，并为 Cursor、OpenCode、Gemini、Zed、GitHub Copilot、Antigravity、Qwen 及其他 harness 提供能力受限的 adapter。在假定 feature parity 之前，请查看 [support status matrix](#platform-support)。

包含 67 个 agents、284 个 skills 和 94 个 legacy command shims，外加 hooks、rules、memory、continuous learning 和 AgentShield 安全扫描。这些 agents 专门用于 planning、review、build repair、security、architecture 和领域工作。

| 包含内容         |       数量 | 它为你提供什么                                                                         |
| ---------------- | ---------: | -------------------------------------------------------------------------------------- |
| Agents           |   67 agents | Planning、review、build repair、security、architecture 以及领域工作                     |
| Skills           |  284 skills | TDD、research、security、docs、frontend、data、ML、operations 等更多                    |
| Commands         | 94 commands | 在 ECC 转向 skills-first surface 期间提供便捷的入口                                 |
| Hooks 和 memory  |     Runtime | Enforcement、session summaries、continuous learning、instincts 以及 context controls |
| Rules            |   选择性加载 | 按语言或项目选择的始终加载的标准                                                   |
| AgentShield      |    已包含 | 扫描 prompts、hooks、MCP config、permissions、secrets 和 agent 文件                  |

## Install ECC

> [!NOTE]
> 以下引导式命令需要 `ecc-universal` 2.2.0 或更新版本。如果 npm 仍然解析到 2.1.0，请使用下面 provider 原生的说明，直到 2.2.0 包发布。

### 每个 harness 只能选择一条路径

你可以同时在 Claude Code、Codex 和其他 harness 中使用 ECC。为每个 harness 选择一种安装方式：

- **推荐默认：** 使用 `npx ecc-universal setup` 运行引导式 Claude plugin setup
- **推荐用于多个 harness：** 运行 `npx ecc-universal install --guided`
- **可行：** Claude Code plugin + Codex 原生 plugin
- **可行：** Claude Code plugin + 旧版 Codex sync 流程
- **避免：** Claude Code plugin + Claude 完全手动安装
- **避免：** Codex sync + Codex marketplace plugin

**切勿堆叠安装方式。** 将 ECC 两次安装到同一个 harness 中可能会使 skills、commands、hooks 或 configuration 重复；将其分别安装到多个 harness 中则不会。

如果你已经叠加了多个安装并且看起来有重复，请直接跳到 [Reset / Uninstall ECC](#reset--uninstall-ecc)。

**安装遇到问题？** 填写简短的 [install or runtime problem form](https://github.com/affaan-m/ECC/issues/new?template=install-problem.yml)，或者运行 `ecc feedback`。ECC 绝不会自动上传诊断信息。

### Guided setup（推荐）

用于 Claude Code plugin setup、更新、scope 变更和 hook-profile 变更：

```bash
npx ecc-universal setup
```

同一个已发布的包与现代包运行器兼容：

| 包运行器 | Guided setup 命令 |
|---|---|
| npm / npx | `npx ecc-universal setup` |
| pnpm | `pnpm dlx ecc-universal setup` |
| Yarn 2+ | `yarn dlx ecc-universal setup` |
| Bun | `bunx ecc-universal setup` |

Yarn Classic 1 不提供 `yarn dlx`；请使用 `npx`，全局安装该包，或者升级 Yarn 以进行临时一次性运行。

该向导会在做出更改之前清查官方 marketplace 和每个原生 Claude 安装 scope，然后在你选择的 scope 中安装、更新或安全迁移 `ecc@ecc`。每当你想要更新 ECC、更改 scope 或更改其 hook profile 时，重新运行相同的命令。此 setup wizard 当前配置 Claude Code plugin；对于 Codex 或 Kimi Code，请使用下面的 multi-harness wizard。

要在一个受审查的流程中配置多个 coding agent，请使用 multi-harness wizard：

```bash
npx ecc-universal install --guided
```

它允许你选择 Claude Code、Codex 和 Kimi Code 的任意组合，显示每个安装渠道和目标，在首次写入前对每个选择进行 preflight，并请求一次最终确认。

| Harness | Guided install 行为 |
|---|---|
| Claude Code | 带有 `user`、`project` 或 `local` scope 和 ECC hook profile 的原生 `ecc@ecc` plugin |
| Codex | 原生 Codex marketplace/plugin 生命周期；hook review 和 trust 仍由 Codex 掌控 |
| Kimi Code | `./.kimi-code` 下的托管项目文件；不配置 ECC hooks、model/provider 设置和 authentication |

为了实现自动化，请明确指定每个 provider 的选项：

```bash
npx ecc-universal install --guided \
  --harness claude --harness codex --harness kimi \
  --claude-scope local --claude-hooks standard \
  --profile core --yes
```

在不写入的情况下验证原生 guided Codex 路径和托管 Kimi 路径：

```bash
npx ecc-universal install --guided --harness codex --dry-run
npx ecc-universal install --profile core --target kimi --dry-run
```

ECC 还为 `cursor`、`antigravity`、`gemini`、`opencode`、`codebuddy`、`joycode`、`qwen`、`zed`、`hermes` 和 `openclaw` 提供了高级托管 adapter。这些目标仍然使用其记录的 `ecc install --target ...` 路径，直到每个 adapter 通过 guided collision、update、repair 和 uninstall 生命周期矩阵测试。两个 wizard 都不会静默安装到每个检测到的 harness 中。

### Claude Code

仅当你特别需要原生路径或无法运行包 wizard 时，才使用 Claude Code 内置的 marketplace 命令：

```text
/plugin marketplace add https://github.com/affaan-m/ECC
/plugin install ecc@ecc
```

这将安装 ECC 的 skills、agents、commands 和 plugin 管理的 hooks。Claude Code 拥有这些内置命令，包括当 marketplace、plugin 或冲突的 scope 已存在时产生的错误。ECC 无法拦截该解析器。如果任一命令报告已有安装或 scope 冲突，请运行 `npx ecc-universal setup`；ECC 拥有的流程会检查当前状态，并选择安装、更新或验证过的 scope 迁移，而不是盲目地添加一个重复项。

安装 ECC 后，`/ecc:configure-ecc` 是命名空间化的 in-Claude 重新配置 skill。它委托给相同的安全 setup 流程，但仅在 plugin 安装后才可用，并且不能在首次安装时替代 Claude Code 的内置 `/plugin` 命令。

Claude Code plugins 无法分发 `rules`，因此仅添加你实际需要的 rule pack：

```bash
git clone https://github.com/affaan-m/ECC.git
cd ECC
mkdir -p ~/.claude/rules/ecc
cp -R rules/common ~/.claude/rules/ecc/
cp -R rules/typescript ~/.claude/rules/ecc/  # 替换为你的技术栈
```

从 `rules/common` 加上一个你实际使用的语言或框架 pack 开始。如果你安装了 plugin，之后切勿运行 `./install.sh --profile full`。

<details>
<summary><strong>更喜欢 settings.json？声明式地添加 marketplace</strong></summary>

直接添加到你的 `~/.claude/settings.json` 中：

```json
{
  "extraKnownMarketplaces": {
    "ecc": {
      "source": {
        "source": "github",
        "repo": "affaan-m/ECC"
      }
    }
  },
  "enabledPlugins": {
    "ecc@ecc": true
  }
}
```

这将为你提供与上面两个 `/plugin` 命令相同的结果。
</details>

<details>
<summary><strong>命名 + 迁移说明 (ecc@ecc, affaan-m/ECC, ecc-universal)</strong></summary>

ECC 有三个公共标识符，它们不可互换：

- GitHub 源码仓库：`affaan-m/ECC`
- Claude marketplace/plugin 标识符：`ecc@ecc`
- npm 包：`ecc-universal`

这是有意为之。Anthropic marketplace/plugin 安装以规范的 plugin 标识符为键，因此 ECC 使用 `ecc@ecc` 来保持工具名称和 slash-command 命名空间足够短，以通过严格的 Desktop/API 验证器。较早的帖子可能仍显示以前较长的 marketplace 标识符；请仅将其视为旧版别名。另外，npm 包保留在 `ecc-universal`，因此 npm 安装和 marketplace 安装有意使用不同的名称。

npm 发布是按版本标签而不是按 commit 进行的，因此 `ecc-universal` 追踪的是 releases（2.1、2.2...）而非每一次向 `main` 的 push。如果你想要最新的前沿版本，请从 git 安装。

如果你本地的 Claude 设置被清除或重置，这并不意味着你需要重新购买任何东西。在重新安装之前，先运行 `node scripts/ecc.js list-installed`，然后运行 `node scripts/ecc.js doctor` 和 `node scripts/ecc.js repair`。这通常可以恢复 ECC 管理的文件，而无需重建你的设置。
</details>

### Codex App 与 CLI

当前的 Codex 版本可以将 ECC 作为原生 repo-marketplace plugin 安装。marketplace 条目使用仓库根目录，以便 Codex 的缓存接收 manifest 以及所有引用的 skills、MCP configuration、hook runtime、scripts 和 assets：

```bash
codex plugin marketplace add affaan-m/ECC
codex plugin add ecc@ecc
codex plugin list --json
node scripts/codex/check-plugin-cache.js
```

这两个 add 命令都是幂等的。要稍后刷新，请运行 `codex plugin marketplace upgrade ecc`，然后运行 `codex plugin add ecc@ecc`。Codex 在活动的 `CODEX_HOME` 中存储一个已启用的 plugin 状态；它不提供 Claude 的 `user`、`project` 和 `local` scope。其原生 hooks 需要明确的 trust 决策，并且不使用 Claude 的四个 ECC hook profile。在 Codex 内部，调用 `$configure-ecc` 以获取引导式的 provider 感知流程。

较旧的 `scripts/sync-ecc-to-codex.sh` 路径仍然是一个单独的兼容性选项，适用于那些有意在 `~/.codex` 中复制和合并配置的用户；原生 plugin 不需要它。首先运行一次 Codex，确保 `~/.codex/config.toml` 存在，然后：

```bash
git clone https://github.com/affaan-m/ECC.git
cd ECC
npm install
bash scripts/sync-ecc-to-codex.sh
```

你也可以直接在 Codex 中打开 ECC 仓库以进行 project-local setup。Codex 会读取根目录的 `AGENTS.md` 和 `.codex/` 中受信任的项目配置，而无需全局同步。切勿在 sync 流程之上再添加原生 marketplace plugin。

有关仓库导航、所有权明确和 PR diff packet 指导，请阅读 [Codex ECC Navigation Map](docs/CODEX-NAVIGATION-GUIDE.md)。有关原生生命周期详细信息，请参见 [.codex plugin notes](.codex-plugin/README.md)。

## Advanced Install Options

这些选项直接放在主要安装路径下方，这样当默认设置不合适时，你不必在整个 README 中搜寻。

<details>
<summary><strong>无 hook runtime 的低上下文安装</strong></summary>

### 低上下文 / 无 hooks 路径

当你需要 ECC 的 rules、agents、commands、platform config 和核心 workflows 而不需要 runtime hooks 时使用：

```bash
./install.sh --profile minimal --target claude
# 或者，无需先克隆
npx ecc-install --profile minimal --target claude
```

Windows：

```powershell
.\install.ps1 --profile minimal --target claude
```

对于禁用 hooks 的正常 core profile：

```bash

```

仅在需要时才稍后添加 hook runtime：

```bash

```

#### 安装 hooks
> **注意：**：以下内容与根目录下的 README.md 中的原文不同，是根据 install.sh 脚本的实际代码和预执行结果验证后修正的。

不要将原始仓库的 `hooks/hooks.json` 复制到 `~/.claude/settings.json` 或 `~/.claude/hooks/hooks.json` 中。要使用 installer 以便将 hook 及所需资源全部拷贝到指定目录下：

```bash

```

该命令将：
  - **拷贝`hooks/` → `~/.claude/hooks/`**（5 文件）
  - **拷贝`scripts/hooks/` → `~/.claude/scripts/hooks/`**（约 50 文件）
  - **拷贝`scripts/lib/` → `~/.claude/scripts/lib/`**（约 123 文件，递归）
  - **替换`~/.claude/hooks/hooks.json`中的`{CLAUDE_PLUGIN_ROOT}`**：读源文件 → 替换 → 回写文件
  - **更新`~/.claude/ecc/install-state.json`**：账本，schema `ecc.install.v1`，记录 target/modules/operations/每文件 contentSha256

如果你通过 `/plugin install` 安装了 ECC，请不要将这些 hooks 复制到 `settings.json` 中。Claude Code v2.1+ 已经自动加载 plugin 的 `hooks/hooks.json`，将他们复制到 `settings.json` 中会导致重复执行和跨平台 hook 冲突。

### Itô compute CLI bridge

`ecc ito` 委托给单独安装的规范 Itô client；ECC 不维护第二个 API client。`ecc ito login [--no-browser]` 执行设备授权，默认打开 Itô 验证页面，并在 macOS Keychain 中持久化 device token；`--no-browser` 会抑制页面跳转。ECC 本身不进行浏览器自动化。`ecc ito auth` 仅验证，并拒绝 `--no-browser`。可用的操作有 `ecc ito login`、`ecc ito auth`、`ecc ito find`、`ecc ito status` 以及单独设限的 `ecc ito evals`。匹配的 MCP tools 保持为 `ito_auth`、`ito_find` 和 `ito_status`；`ito_auth` 验证现有凭证，节点资格认证仅限于 CLI。

`ito-compute-cli` 包目前尚未发布。从 Itô runtime 仓库（在 desk 加固期间为私有仓库；设计合作伙伴可获取访问权限）在 `cli/ito-compute-cli` 下本地构建它，运行 `npm ci` 和 `npm run check`，然后将 `ECC_ITO_CLI_EXECUTABLE` 设置为该构建的绝对路径 `dist/bin/ito.js`。Login 绝不会继承 `ITO_API_KEY`；auth、find 和 status 在配置后会直接转发 `ITO_API_KEY`，并且不需要 `ITO_AUTH_MODE=legacy`。`ecc ito logout` 会撤销当前的 device credential，如果无法确认远程撤销，则会保留其本地副本。Device tokens 默认使用 macOS Keychain；显式的文件回退必须保留仅限所有者的目录/文件权限。ECC 不会通过 `PATH` 发现这个承载凭证的 client。有关完整的 RFQ 授权和 MCP setup 约定，请参阅 [`ito-compute` skill](skills/ito-compute/SKILL.md)。

`find` 会提交一个实时的、经过身份验证的 RFQ。它不会预留容量。`evals` 需要同时设置 `ITO_ENABLE_SIXTYTWO_LIVE=1` 和 `--live-sixtytwo`，一个单独安装的 `sixtytwo-cli==0.3.33`，一个明确的节点列表，以及一个现有的绝对配置目录。它不能租用、启动、恢复、修复或购买。ECC 不暴露任何报价锁定、购买、工作负载或推理路径，并且它从不以本地结果替代缺失的 client 或失败的实时调用。

### Reset / Uninstall ECC

如果 ECC 感觉重复、侵入性或已损坏，请在重新安装前检查托管状态：


Plugin 用户应从 Claude Code 中移除 plugin，然后只删除他们手动复制且不再需要的 rule 文件夹。ECC 只移除其 install-state 中记录的文件。它不会认领你的 harness 目录中不相关的文件。

如果你堆叠了安装方式，请按以下顺序清理：

1.  移除 Claude Code plugin 安装。
2.  从仓库根目录运行 ECC uninstall 命令，以移除 install-state 管理的文件。
3.  删除你手动复制且不再需要的任何额外 rule 文件夹。
4.  使用单一路径重新安装一次。

## 为什么选择 ECC？

| 没有系统时 | 使用 ECC 后 |
|---|---|
| Plan 消失在聊天记录中 | Plan 在实现开始前成为可编辑的工件 |
| "请使用 TDD" 是模型可能忘记的一条指令 | TDD 变成一个有证据支持的受控 `RED -> GREEN -> REFACTOR` 工作流 |
| 同一个 context 既写代码又审查代码 | 一个 fresh-context reviewer 查找 regression 和盲点 |
| Memory 意味着保存巨大的 transcript | Sessions 被提炼为 summaries、instincts 和可复用的 skills |
| 质量检查依赖于提醒 | Hooks 可以在 prompt 之外强制执行确定性检查 |
| Agent 配置默认受信任 | AgentShield 将 harness 本身作为一个攻击面进行扫描 |

### TDD：Test-Driven Development

```text
/ecc:plan "添加基于使用量的计费警报"
  -> 确认或编辑 plan
  -> 激活 tdd-workflow
  -> 在实现前捕获 RED 证据
  -> 实现直到 GREEN
  -> 从 fresh context 审查
  -> 用 regression tests 修复发现的问题
  -> 验证 build、lint、types 和 tests
```

结果不仅仅是代码。它是一串证据：plan、失败的 test、通过的 test、审查发现以及最终验证。

### Skills 保持 context 聚焦

Rules、skills、agents 和 hooks 解决不同的问题。将这些职责分开是 ECC 在不将整个仓库倾倒到每个 session 中的情况下增加能力的方式。

| 概念 | 它做什么 | Context 行为 |
|---|---|---|
| Skills | 可复用的 workflows，例如 TDD、security review 或 deep research | 在任务需要时加载 |
| Agents | 具有自己 context 和 tool 权限的限定范围工作者 | 隔离 planning、implementation 和 review |
| Rules | 持久的项目或语言标准 | 始终加载，因此要有选择地安装 |
| Hooks | 由 harness 事件触发的脚本 | 在模型 context 之外运行 |
| Instincts | 从真实 sessions 中学到的具有 confidence scores 的模式 | 在相关时被召回 |

### 在 harness 之间共享 context

ECC 的 Memory Vault 为 Claude、Codex、Hermes、OpenClaw、Kimi 和其他 harness 提供一种本地、可检查的 Markdown 格式，用于持久 context 和 handoffs。项目和团队 memory 存放在 `.ecc/memory/` 下；用户 memory 存放在 `~/.ecc/memory/` 下。

```bash
npm install -g ecc-universal
ecc memory init --scope project
ecc memory search "authentication migration" --target-harness codex
ecc memory doctor
```

Memory 是未经审查的 context，不是可执行策略。请根据权威来源验证重要声明，并将已接受的知识提升到受治理的项目文档中。可选的 `ecc-memory-mcp` server 公开相同的受限 save、search、read 和 doctor 界面，默认不自启用。

[打开 Unified Memory workflow →](skills/unified-memory/SKILL.md)

<details>
<summary><strong>Memory Vault 深入：scopes、handoffs 和信任边界</strong></summary>

Memory Vault 存储可移植的 `ecc.memory.v1` Markdown 文档，而不是复制供应商 transcripts 或在 agent 之间通过电子邮件发送 context。Project memories 受 fail-closed `.gitignore` 保护；仅将 team scope 用于经过人工检查、版本控制的共享。Team memories 即使在提交后也仍然是未经审查的 context。

Skill-only、minimal、manual 和 Claude plugin 安装不会将 Memory Vault runtime 放在 `PATH` 上。在使用 CLI 或可选的 MCP server 之前，请单独安装 npm runtime：

```bash
npm install -g ecc-universal
ecc memory --help
command -v ecc-memory-mcp
```

```bash
# 初始化项目 vault。
ecc memory init --scope project

# 将 handoff 正文写入常规文件，然后针对下一个 harness。
ecc memory handoff \
  --from hermes \
  --target codex \
  --title "继续身份验证迁移" \
  --body-file ./handoff.md

# 从另一个 harness 召回它。
ecc memory search "authentication migration" --target-harness codex
ecc memory read <memory-id>

# 在共享 team memories 之前验证 vault。
ecc memory doctor
```

Memory 正文只能通过 `--stdin` 或 `--body-file` 接受，不能作为命令行值。第一个版本将每个 vault 条目保持为未经审查且仅创建；人工审查会将已接受的知识提升到受治理的项目文档中，而不是更改 memory trust。正常的 search recall 返回活动的 project 和 team memories。直接 ID read 可以检查非活动条目。User-scope recall 必须显式请求。Agents 必须根据权威来源验证重要声明，并且绝不能将召回的正文视为可执行指令或策略。

对于 opt-in MCP 访问，将来自 [`mcp-configs/mcp-servers.json`](mcp-configs/mcp-servers.json) 的 `ecc-memory-vault` 条目添加到每个需要的 harness 中，然后运行 `ecc-memory-mcp`。该 server 仅公开 `memory_save`、`memory_search`、`memory_read` 和 `memory_doctor`。每个 server 必须以小写的 `ECC_MEMORY_HARNESS` 身份启动；该身份是 server 绑定的，不能由 tool caller 提供。User scope 额外需要由操作员控制的 `ECC_MEMORY_ALLOW_USER_SCOPE=1` opt-in。有关 workflow 和信任边界，请参见 [`skills/unified-memory/SKILL.md`](skills/unified-memory/SKILL.md)；有关能力约定，请参见 [`docs/design/ecc-memory-vault.md`](docs/design/ecc-memory-vault.md)。

## 关键概念

<details>
<summary><strong>Agents、skills、hooks 和 rules 解释</strong></summary>

### Agents

Subagents 处理具有有限 scope 的委托任务。示例：

```markdown
---
name: code-reviewer
description: 审查代码的质量、安全性和可维护性
tools: Read, Grep, Glob, Bash
model: opus
---

你是一名高级代码审查员...
```

### Skills

Skills 是主要的工作流界面。它们可以被直接调用、自动建议，并由 agents 复用。ECC 在迁移期间仍然提供维护的 `commands/`，而已退役的短名 shims 存放在 `legacy-command-shims/` 中，仅供显式 opt-in。新的 workflow 开发应首先落地在 `skills/` 中。

```markdown
# TDD Workflow

1. 首先定义接口
2. 编写失败的 tests (RED)
3. 实现最简代码 (GREEN)
4. 重构 (IMPROVE)
5. 验证 80%+ coverage
```

### Hooks

Hooks 在 tool 事件上触发。示例：警告关于 console.log：

```json
{
  "matcher": "tool == \"Edit\" && tool_input.file_path matches \"\\\\.(ts|tsx|js|jsx)$\"",
  "hooks": [{
    "type": "command",
    "command": "#!/bin/bash\ngrep -n 'console\\.log' \"$file_path\" && echo '[Hook] 移除 console.log' >&2"
  }]
}
```

### Rules

Rules 是始终遵循的指南，组织为 `common/`（语言无关）+ 语言特定目录：

```
rules/
  common/          # 通用原则（始终安装）
  typescript/      # TS/JS 特定模式和工具
  python/          # Python 特定模式和工具
  golang/          # Go 特定模式和工具
  swift/           # Swift 特定模式和工具
  php/             # PHP 特定模式和工具
  arkts/           # HarmonyOS / ArkTS 模式和约束
```

有关安装和结构详细信息，请参见 [`rules/README.md`](rules/README.md)。
</details>

## 跨平台支持

ECC 的核心 Node.js CLI 和托管 installers 可在 **Windows、macOS 和 Linux** 上运行，但可选功能的 parity 并不完整。一些 continuous-learning、GAN 和 orchestration 路径仍需要 Bash 或 Python；harnesses 也公开不同的 hook、agent 和 skill API。

| 平台 | 状态 | 当前限制 |
|---|---|---|
| Linux | 支持核心 | 可选功能可能需要 Bash、Python 或特定 provider 工具。 |
| macOS | 支持核心 | 独立的 GAN shell 路径与系统 Bash 3.2 不兼容，目前存在 score-parsing defect ([#2674](https://github.com/affaan-m/ECC/issues/2674))。 |
| Windows + WSL | 支持核心 | WSL 遵循 Linux 路径；Windows 主机集成仍因 harness 而异。 |
| Windows native | 有限支持 | Continuous-learning v2 的 observer daemon 和 memory-vault 写入存在开放的原生 Windows defects ([#2489](https://github.com/affaan-m/ECC/issues/2489), [#2626](https://github.com/affaan-m/ECC/issues/2626))。Shell 支持的可选功能需要 Git Bash/WSL 或不可用。 |

将下方的 `stable`、`beta`、`experimental` 和 `instruction-only` 视为能力声明，而非营销层级。

<details>
<summary><strong>包管理器检测</strong></summary>

plugin 会自动检测你首选的包管理器（npm、pnpm、yarn 或 bun），优先级如下：

1.  **环境变量**：`CLAUDE_PACKAGE_MANAGER`
2.  **项目配置**：`.claude/package-manager.json`
3.  **package.json**：`packageManager` 字段
4.  **Lock file**：从 package-lock.json、yarn.lock、pnpm-lock.yaml 或 bun.lockb 检测
5.  **全局配置**：`~/.claude/package-manager.json`
6.  **回退**：第一个可用的包管理器

设置你的首选包管理器：

```bash
# 通过环境变量
export CLAUDE_PACKAGE_MANAGER=pnpm

# 通过全局配置
node scripts/setup-package-manager.js --global pnpm

# 通过项目配置
node scripts/setup-package-manager.js --project bun

# 检测当前设置
node scripts/setup-package-manager.js --detect
```

或者使用 `/setup-pm` 命令。
</details>

<details>
<summary><strong>Hook runtime 控制（环境变量）</strong></summary>

使用 runtime flags 来调整严格性或临时禁用特定 hooks：

```bash
# Hook strictness profile（默认：standard）
export ECC_HOOK_PROFILE=standard

# 要禁用的 hook ID，以逗号分隔
export ECC_DISABLED_HOOKS="pre:bash:tmux-reminder,post:edit:typecheck"

# SessionStart 附加上下文上限（默认：8000 字符）
export ECC_SESSION_START_MAX_CHARS=4000

# 为低上下文/本地模型设置完全禁用 SessionStart 附加上下文
export ECC_SESSION_START_CONTEXT=off

# Session-tmp 保留窗口（天）（默认：30）。
# 设置为 0、off、false、disabled、never 或 none 以保留所有 sessions（禁用修剪）。
export ECC_SESSION_RETENTION_DAYS=14

# SessionStart 注入到 context 中的 learned instincts 数量上限（默认：6）
export ECC_MAX_INJECTED_INSTINCTS=6

# 一个 instinct 被注入所需的最低 confidence，0-1（默认：0.7）
export ECC_INSTINCT_CONFIDENCE_THRESHOLD=0.7

# 保留 context/scope/loop 警告，但抑制 API-rate 成本估算
export ECC_CONTEXT_MONITOR_COST_WARNINGS=off
```

Windows PowerShell：

```powershell
[Environment]::SetEnvironmentVariable('ECC_CONTEXT_MONITOR_COST_WARNINGS', 'off', 'User')
[Environment]::SetEnvironmentVariable('ECC_SESSION_RETENTION_DAYS', '14', 'User')
```
</details>

<details>
<summary><strong>Agent data home（多 harness 隔离）</strong></summary>

Memory persistence hooks（session summaries、learned skills、session aliases、metrics）将数据存储在一个 agent data root 下。默认情况下，该根目录是 `~/.claude`。当你在同一台机器上同时在 Claude Code 和 Cursor 中使用 ECC 时，为 Cursor 设置一个单独的根目录，这样两个环境就不会互相覆盖对方的 session 文件：

```bash
# 仅限 Cursor 的边界（Claude Code 保持默认的 ~/.claude）
export ECC_AGENT_DATA_HOME="$HOME/.cursor/ecc"
```

在该根目录下解析的路径包括：

- `$ECC_AGENT_DATA_HOME/session-data/`：session summaries
- `$ECC_AGENT_DATA_HOME/skills/learned/`：从 evaluate-session 学到的 skills
- `$ECC_AGENT_DATA_HOME/session-aliases.json`：session aliases
- `$ECC_AGENT_DATA_HOME/metrics/`：成本和活动 metrics

请参见 [affaan-m/ECC#2065](https://github.com/affaan-m/ECC/issues/2065)。
</details>

| Codex | Supported sync; marketplace experimental | 仓库配置或 `sync-ecc-to-codex.sh` | 无 ECC hook runtime。marketplace 包可能会从 Codex 的缓存中遗漏共享的仓库内容；对于可靠路径，使用 sync。 |
| Cursor | Beta project adapter | 使用 selective installer 安装到 `.cursor/` | Agent discovery 因 Cursor build 而异，并且 ECC 的 installer 路径尚未公开相同的 hook sets ([#2419](https://github.com/affaan-m/ECC/issues/2419))。 |
| OpenCode | Beta built plugin | 构建 plugin，然后 selective installer | ECC 提供了目录的一个子集，并且参考配置固定了 Anthropic 模型；请选择你的 provider 可用的模型 ([#2617](https://github.com/affaan-m/ECC/issues/2617))。 |
| GitHub Copilot | Instruction-only | 已检入的 instructions 和 prompt 文件 | 无 ECC hooks、runtime agents、delegation 或原生 skill discovery。 |
| Gemini、Zed、Antigravity、Qwen、Hermes、OpenClaw、Kimi、CodeBuddy、JoyCode | Experimental/minimal adapters | 特定于 harness 的 selective target | 文件放置和指令可移植性已经过测试；不声称具有完整的 Claude feature parity。 |

### 跨工具能力映射

| 能力 | Claude Code | Codex | Cursor | OpenCode | GitHub Copilot |
|---|---|---|---|---|---|
| Instructions | Native | 原生 `AGENTS.md` | Project rules | Plugin instructions | 原生 instruction file |
| Skills | Native installed set | Native synced set | Build-dependent/project set | Built subset | 仅 Prompt/instruction 引用 |
| Agents/delegation | Native agents | Codex multi-agent roles | Build-dependent project agents | Plugin agents | 不支持 |
| ECC hooks | Native plugin hooks | 不支持 | Cursor hook adapter；安装路径差异仍然存在 | Plugin events | 不支持 |
| MCP configuration | 可用，显式激活 | 通过 sync 进行 TOML merge | 显式 project/user config | Provider/plugin config | ECC 不提供 |
| 与 Claude Code 的一致性 | 主要参考 | 部分 | 部分 | 部分 | 非一致性目标 |

**关键架构决策：**
-   根目录下的 **AGENTS.md** 是通用跨工具文件（由 Claude Code、Cursor、Codex 和 OpenCode 读取；GitHub Copilot 改为使用 `.github/copilot-instructions.md`）
-   **DRY adapter pattern** 允许 Cursor 复用 Claude Code 的 hook scripts，无需重复
-   **Skills 格式**（带有 YAML frontmatter 的 SKILL.md）跨 Claude Code、Codex 和 OpenCode 工作
-   Codex 缺少 hooks 通过 `AGENTS.md`、可选的 `model_instructions_file` 覆盖以及 sandbox permissions 来弥补

#### Cursor 加载说明

ECC 不会将根目录的 `AGENTS.md` 安装到 `.cursor/` 中。Cursor 将嵌套的 `AGENTS.md` 文件视为目录 context，因此将 ECC 的仓库身份复制到宿主项目会污染该项目。

Cursor 原生的加载行为可能因 Cursor build 而异。ECC 将 agents 安装为 `.cursor/agents/ecc-*.md`；如果你的 Cursor build 不公开项目 agents，这些文件仍然可以作为显式参考定义，而不是隐藏的全局 prompt context。

#### Memory 和数据隔离（Cursor + Claude Code）

ECC memory hooks 复用与 Claude Code 相同的 `scripts/hooks/*.js`。对于 Cursor，ECC 尝试**自动**将 memory 保持在 `~/.claude` 之外：

1.  **Cursor `sessionStart` hook**（在 `--target cursor` 时安装到 `.cursor/hooks.json`）会为整个 composer session 注入 `ECC_AGENT_DATA_HOME`。
2.  **Hook runtime 默认值**：当存在 `CURSOR_VERSION` 或 `CURSOR_PROJECT_DIR` 时，如果未设置环境变量，hooks 默认使用 `~/.cursor/ecc`。
3.  **项目配置**：`.cursor/ecc-agent-data.json` 记录并覆盖路径 (`agentDataHome`)。
4.  **始终开启的 rule**：`.cursor/rules/ecc-agent-data-home.mdc` 提醒 agent memory 所在的位置。

你仍然可以显式覆盖：

```bash
export ECC_AGENT_DATA_HOME="$HOME/.cursor/ecc"
```

要**有目的地**与 Claude Code **共享** memory，请在 shell 中或在 `.cursor/ecc-agent-data.json` 中设置 `ECC_AGENT_DATA_HOME=~/.claude`。

Continuous learning v2 instincts 在 `CLV2_HOMUNCULUS_DIR`（默认 `~/.local/share/ecc-homunculus`）下保持独立。

#### Hook 架构（DRY adapter pattern）

Cursor 拥有**比 Claude Code 更多的 hook events**（20 对 8）。`.cursor/hooks/adapter.js` 模块将 Cursor 的 stdin JSON 转换为 Claude Code 的格式，允许现有的 `scripts/hooks/*.js` 被复用，无需重复。

```
Cursor stdin JSON -> adapter.js -> 转换 -> scripts/hooks/*.js
                                                （与 Claude Code 共享）
```

关键 hooks：
-   **beforeShellExecution**：阻止在 tmux 外部的 dev servers（exit 2），git push review
-   **afterFileEdit**：自动格式化 + TypeScript 检查 + console.log 警告
-   **beforeSubmitPrompt**：检测 prompts 中的 secrets（sk-、ghp_、AKIA 模式）
-   **beforeTabFileRead**：阻止 Tab 读取 .env、.key、.pem 文件（exit 2）
-   **beforeMCPExecution / afterMCPExecution**：MCP audit logging

#### Rules 格式

Cursor rules 使用带有 `description`、`globs` 和 `alwaysApply` 的 YAML frontmatter：

```yaml
---
description: "TypeScript 编码风格，扩展 common rules"
globs: ["**/*.ts", "**/*.tsx", "**/*.js", "**/*.jsx"]
alwaysApply: false
---
```

## Token 优化

如果你不管理 token consumption，agent 使用可能会很昂贵。这些设置可以在不牺牲质量的情况下显著降低成本。完整指南：[docs/token-optimization.md](docs/token-optimization.md)。

<details>
<summary><strong>推荐设置</strong></summary>

添加到 `~/.claude/settings.json`：

```json
{
  "model": "sonnet",
  "env": {
    "MAX_THINKING_TOKENS": "10000",
    "CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "50",
    "CLAUDE_CODE_SUBAGENT_MODEL": "haiku"
  }
}
```

| 设置 | 默认值 | 推荐值 | 影响 |
|---------|---------|-------------|--------|
| `model` | opus | **sonnet** | 约 60% 成本降低；处理 80% 以上的编码任务 |
| `MAX_THINKING_TOKENS` | 31,999 | **10,000** | 每个请求隐藏的 thinking cost 减少约 70% |
| `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` | 95 | **50** | 更早 compact，在长 sessions 中质量更好 |
| `ECC_CONTEXT_MONITOR_COST_WARNINGS` | on | **对于订阅用户为 off** | 抑制面向 agent 的 API-rate 估算警告，同时保留 context/scope/loop 警告 |

仅在需要深度架构推理时才切换到 Opus：
```
/model opus
```
</details>

<details>
<summary><strong>日常工作流命令</strong></summary>

| 命令 | 何时使用 |
|---------|-------------|
| `/model sonnet` | 大多数任务的默认值 |
| `/model opus` | 复杂架构、调试、深度推理 |
| `/clear` | 在不相关的任务之间（免费、即时重置） |
| `/compact` | 在逻辑任务断点处（研究完成、里程碑完成） |
| `/cost` | 在 session 期间监控 token 支出 |

如果你使用订阅并且 context monitor 的 API-rate 估算没有用，请设置 `ECC_CONTEXT_MONITOR_COST_WARNINGS=off`。这只会抑制面向 agent 的成本警告；它不会禁用 context 耗尽、scope 或 loop 警告。
</details>

<details>
<summary><strong>策略性 compaction</strong></summary>

`strategic-compact` skill 建议在逻辑断点处使用 `/compact`，而不是依赖在 95% context 时的自动 compaction。有关完整的决策指南，请参见 `skills/strategic-compact/SKILL.md`。

**何时 compact：**
-   研究/探索之后，实现之前
-   完成一个里程碑之后，开始下一个之前
-   调试之后，继续功能工作之前
-   一种失败的方法之后，尝试新方法之前

**何时不要 compact：**
-   实现中途（你会丢失变量名、文件路径、部分状态）
</details>

<details>
<summary><strong>Context window 管理</strong></summary>

**关键：** 不要一次启用所有 MCPs。每个 MCP tool 描述都会从你的 200k window 中消耗 tokens，可能将其减少到 ~70k。

-   每个项目保持启用少于 10 个 MCPs
-   保持活跃 tools 少于 80 个
-   使用 `/mcp` 禁用未使用的 Claude Code MCP servers；这些运行时选择会持久化在 `~/.claude.json` 中
-   仅在安装/同步流程中使用 `ECC_DISABLED_MCPS` 来过滤 ECC 生成的 MCP configs
-   如果 context 变得沉重，运行 `/context-budget` 并移除你不需要的 rules

**Agent teams 成本警告：** Agent Teams 会生成多个 context windows。每个团队成员独立消耗 tokens。仅在并行性提供明显价值的任务中使用（多模块工作、并行审查）。对于简单的顺序任务，subagents 在 token 方面更高效。
</details>

### 重要提示：hooks 自动加载行为

<details>
<summary><strong>Hooks、MCP servers 和 context controls</strong></summary>

Hooks 可以运行 shell 命令，MCP servers 可以持有凭证，项目 instructions 可以进入 agent 的 context。将所有三者视为可执行配置。

在 plugin 安装后，不要将原始 `hooks/hooks.json` 复制到 `~/.claude/settings.json` 中。现代 Claude Code 版本会自动加载 plugin hooks，而第二个副本可能使它们触发两次。

使用 `/mcp` 进行 Claude Code 运行时禁用；Claude Code 将这些选择持久化在 `~/.claude.json` 中。

`ECC_DISABLED_MCPS` 是一个 ECC 安装/同步过滤器，而不是实时的 Claude Code toggle。

如果 context 变得沉重，运行 `/context-budget`，移除你不需要的 rules，并禁用未使用的 MCP servers。请参见 [token optimization guide](docs/token-optimization.md)。
</details>

## 故障排除

<details>
<summary><strong>ECC 出现两次或 hooks 触发两次</strong></summary>

通常的原因是在安装 Claude plugin 之后又在其上运行了 `install.sh --profile full` 或 `npx ecc-install --profile full`。

1.  移除 Claude Code plugin 安装。
2.  从 ECC checkout 运行 `node scripts/ecc.js uninstall --dry-run`。
3.  删除你手动复制且不再需要的额外 rule 文件夹。
4.  使用一条路径重新安装一次。

有关 hook 特定的检查，请参见 [hooks README](hooks/README.md)。
</details>

<details>
<summary><strong>我的 hooks 不工作 / "Duplicate hooks file" 错误</strong></summary>

**不要向 `.claude-plugin/plugin.json` 添加 `"hooks"` 字段。** Claude Code v2.1+ 会自动从已安装的 plugins 加载 `hooks/hooks.json`。显式声明它会导致 duplicate detection 错误。请参见 [#29](https://github.com/affaan-m/ECC/issues/29)，[#52](https://github.com/affaan-m/ECC/issues/52)，[#103](https://github.com/affaan-m/ECC/issues/103)。
</details>

<details>
<summary><strong>Codex marketplace 安装成功但 skills 不加载</strong></summary>

从 ECC checkout 运行缓存检查：

```bash
node scripts/codex/check-plugin-cache.js
```

如果它报告未解析的父引用，请使用 `bash scripts/sync-ecc-to-codex.sh`。在 `codex plugin list` 中注册确认了 marketplace 条目，但并未确认每个引用的文件都到达了 plugin cache。来自本地/仓库 marketplaces 的运行时 skill 加载在上游仍然不可靠 ([openai/codex#26037](https://github.com/openai/codex/issues/26037))；请参见 [#2128](https://github.com/affaan-m/ECC/issues/2128) 的完整调查。
</details>

<details>
<summary><strong>我的 context window 在缩小</strong></summary>

过多的 MCP servers 会消耗你的 context。每个 MCP tool 描述都会从你的 200k window 中消耗 tokens，可能将其减少到 ~70k。SessionStart context 默认上限为 8000 字符；使用 `ECC_SESSION_START_MAX_CHARS=4000` 降低它，或者对于本地模型或低上下文设置，使用 `ECC_SESSION_START_CONTEXT=off` 禁用它。

**修复：** 使用 `/mcp` 从 Claude Code 禁用未使用的 MCPs。Claude Code 将这些运行时选择写入 `~/.claude.json`；`.claude/settings.json` 和 `.claude/settings.local.json` 对于已加载的 MCP servers 不是可靠的开关。

保持启用少于 10 个 MCPs，活跃 tools 少于 80 个。
</details>

<details>
<summary><strong>我可以只使用部分组件（例如，仅 agents）吗？</strong></summary>

可以。使用 [Advanced Install Options](#advanced-install-options) 中的手动组件副本，并仅复制你需要的内容：

```bash
# 仅 agents
cp agents/*.md ~/.claude/agents/

# 仅 rules
mkdir -p ~/.claude/rules/ecc/
cp -r rules/common ~/.claude/rules/ecc/
```

每个组件都是完全独立的。
</details>

<details>
<summary><strong>这适用于 Cursor / OpenCode / Codex / Antigravity / GitHub Copilot 吗？</strong></summary>

是的。ECC 是跨平台的：
-   **Cursor**：`.cursor/` 中的预翻译配置。请参见 [Platform Support](#platform-support)。
-   **Gemini CLI**：通过 `.gemini/GEMINI.md` 和共享的 installer plumbing 提供实验性的 project-local 支持。
-   **OpenCode**：`.opencode/` 中的 beta plugin 集成；provider model 选择和 catalog parity 仍然有限。
-   **Codex**：针对 macOS app 和 CLI 的受支持 repo/sync 路径；ECC 的 marketplace 包仍处于实验阶段。
-   **GitHub Copilot (VS Code)**：通过 `.github/copilot-instructions.md`、`.vscode/settings.json` 和 `.github/prompts/` 提供 instruction 和 prompt 层。
-   **Antigravity**：在 `.agent/` 中为 workflows、skills 和 flattened rules 紧密集成设置。请参见 [Antigravity Guide](docs/ANTIGRAVITY-GUIDE.md)。
-   **JoyCode / CodeBuddy**：用于 commands、agents、skills 和 flattened rules 的 project-local selective install adapters。请参见 [JoyCode Adapter Guide](docs/JOYCODE-GUIDE.md)。
-   **Qwen CLI**：用于 commands、agents、skills、rules 和 Qwen config 的主目录 selective install adapter。请参见 [Qwen CLI Adapter Guide](docs/QWEN-GUIDE.md)。
-   **Zed**：用于 `.zed/settings.json`、flattened rules、commands、agents 和 skills 的 project-local selective install adapter。
-   **Non-native harnesses**：用于聊天式界面的手动回退路径。请参见 [Manual Adaptation Guide](docs/MANUAL-ADAPTATION-GUIDE.md)。
-   **Claude Code**：原生。这是主要目标。
</details>

<details>
<summary><strong>我的平台未列出</strong></summary>

使用 [manual adaptation guide](docs/MANUAL-ADAPTATION-GUIDE.md)，或开启一个 [GitHub discussion](https://github.com/affaan-m/ECC/discussions)，并附上 harness 名称及其支持的文件、skill、command 和 hook 格式。
</details>
