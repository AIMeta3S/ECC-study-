# 评估标准 — 详细评分指南

本参考文档为每个评估维度提供具体的评分锚点。当你不确定某个差距应评 4 分还是 3 分、2 分还是 1 分时使用。

## 准确性

| 分数 | 锚点 | 示例 |
|---|---|---|
| 5 | 所有事实都通过 tool 输出、文档或权威来源验证。无错误。 | 通过 httpx transport 配置 retry —— 已在 httpx 文档中确认。所有方法名都通过 grep 对 codebase 验证。 |
| 4 | 一个不影响正确性的轻微不准确。 | 库正确，但某个 parameter 的默认值有误（声称 0.5s，文档显示 1.0s）。 |
| 3 | 一个重大事实错误，或 3 个以上轻微不准确。 | 在 httpx codebase 中使用了 `urllib3.Retry`。在该场景下能工作，但选错了库。 |
| 2 | 多个重大错误。按此执行的 output 会失败。 | 声称"将此添加到 package.json"但项目使用 pyproject.toml。另外两处 config 声明也有误。 |
| 1 | 根本性错误。output 自相矛盾或与已知事实相悖。 | 代码存在语法错误。API endpoint 不存在。声称的函数签名被 grep 推翻。 |

## 完整性

| 分数 | 锚点 | 示例 |
|---|---|---|
| 5 | 所有显式和隐式需求都已覆盖。edge case 已处理。error path 已处理。 | 用户说"为所有 HTTP 请求添加 retry"。GET、POST、PUT、DELETE 全部覆盖。Timeout、429、5xx 全部处理。 |
| 4 | 所有显式需求都已覆盖。遗漏一个隐式需求。 | 所有 HTTP method 都已覆盖。忘记处理 connection timeout（未提及但属于预期）。 |
| 3 | 遗漏一个显式需求，或 2 个以上隐式缺口。 | 用户说"也添加 logging"。添加了 retry 逻辑但没有 logging。 |
| 2 | 遗漏多个显式需求。output 只是部分解决方案。 | 要求 retry + circuit breaker。只实现了 retry。 |
| 1 | 遗漏核心请求。交付的内容偏离了所要求的。 | 要求 retry 逻辑。却写了一个 health check endpoint。 |

## 清晰度

| 分数 | 锚点 | 示例 |
|---|---|---|
| 5 | 结构完美。专业术语已解释或已避免。视觉层次有助于扫读。无歧义。 | README 有清晰的章节、代码块，顶部还有 10 秒摘要。 |
| 4 | 总体清晰。某一部分组织可以更好，或某个术语未定义。 | 结构良好，但使用了 `exponential backoff` 却未解释 —— 假设读者已知。 |
| 3 | 重读后可理解。多处组织问题或术语未定义。 | 解释绕了一圈才说到重点。多个术语在定义前就使用。 |
| 2 | 部分内容令人困惑。读者需要追问。 | 代码可工作，但 PR 描述没有解释为什么需要 retry 或修复了什么。 |
| 1 | 不可理解或自相矛盾。读者无法判断做了什么或为什么。 | output 是一大段没有结构的文字。结论与前面的陈述相矛盾。 |

## 可操作性

| 分数 | 锚点 | 示例 |
|---|---|---|
| 5 | 只需单一动作。包含验证路径。无隐式步骤。 | "合并此 PR。测试通过：`42 passed`。用 `./deploy.sh` 部署。" |
| 4 | 只需单一动作，但验证路径是隐式的，未明确说明。 | "合并此 PR。"（测试存在但未引用。用户必须自己检查。） |
| 3 | 需要多个动作，或一个动作但下一步不明确。 | "审查并合并。然后更新 config。"（哪个 config？在哪？没有链接或路径。） |
| 2 | 用户必须自己弄清楚如何使用 output。缺少关键指令。 | 代码已写但没有 test 文件，没有运行说明，没有创建 PR。用户必须自己组装一切。 |
| 1 | 不经过大量返工或澄清，output 无法被执行。 | "这是一个设计想法。"（没有代码、文件、PR。用户必须从零开始。） |

## 简洁性

| 分数 | 锚点 | 示例 |
|---|---|---|
| 5 | 每一句都有其价值。无冗余。信息密度高。 | 30 行就说清了 60 行才能说完的内容。无重复观点。无填充内容。 |
| 4 | 轻微冗余。某一段可以精简。 | 总体良好，但在 PR 描述和代码注释中重复了动机说明。 |
| 3 | 明显冗余。20% 以上的内容可删除而不损失信息。 | 同一概念解释了三次（在摘要、正文和结论中）。示例冗长。 |
| 2 | 严重臃肿。40% 以上的内容是填充或重复。 | 200 行应对一个只需 60 行的任务。重述用户的问题。包含无关的背景。 |
| 1 | 信噪比倒置。填充内容多于实质内容。 | 对一个 2 行问题的 500 行回复。大部分是套话、重复或无关上下文。 |

## Edge Cases

### 当用户给出不清晰的指令时

如果用户的请求含糊不清，不要因为无法读心而对完整性扣分。相反，应在评估中注明："用户的请求在 [范围] 上含糊不清。我选择了 [所选解释] 这一解释。如果他们指的是 [替代解释]，此分数将降至 [分数]。"

### 当任务本身很简单时

一个 3 行的 bug fix 完全可以合理地得到 5/5/5/5/5 的评分。rubric 随复杂度调整 —— 完美完成的简单任务就是 5.0。不要为了给低分找理由而编造差距。

### 当你在任务过程中发现自己的错误时

如果你犯了错，并在交付前发现并修复 —— 最终 output 的准确性评分为 5。评估关注的是用户收到了什么，而非你的内部过程。将自我修正作为严谨的证据，而非扣分项。

### 当 tool 输出与你的声明相矛盾时

如果你声称"测试通过"，但终端输出显示失败 —— 准确性自动 ≤ 2。tool 输出即为事实依据。未经验证的声明是低准确性分数最常见的来源。
