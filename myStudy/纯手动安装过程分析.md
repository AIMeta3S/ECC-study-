# ECC 手动安装机制分析（`./install.sh --profile full`）

> 本文以实际源码 + `--dry-run` 实测为唯一依据（不依赖 README 等二手文档），系统讲解 `./install.sh --profile full` 对本机做了什么、怎么做的、效果如何。
>
> - 仓库版本：[plugin.json](../.claude-plugin/plugin.json) `version` = **2.2.0**（官方自报 *"67 agents, 284 skills, 94 legacy command shims"*）。
> - 默认 `--target claude`，安装根 = `~/.claude/`，状态文件 = `~/.claude/ecc/install-state.json`。
> - 文中数字均为当前版本的 dry-run 实测值；随仓库演进可能变化，文末给出复现命令。

---

## 一、本质：纯文件复制式安装

`./install.sh --profile full` 是**纯文件复制式安装**：按 `full` profile 精选仓库内容，把文件**复制**到 `~/.claude/` 下，**不修改任何已有配置**。

实证（`node scripts/install-apply.js --profile full --dry-run --json`）：
- 共 **1003** 个文件操作，`kind` **全部是 `copy-file`**，**0 个 `merge-json`**；
- 全链路从不写 `~/.claude/settings.json`（installer 代码里零处写入）。

`merge-json` 才会深度合并并改写已有 JSON；claude target 的 adapter 只生成 `copy-file` 操作（见 [第三节](#三路径映射规则targetclaude)），所以 `settings.json`、`.mcp.json`、`CLAUDE.md`、shell 配置、环境变量一律不动。唯一例外是 ECC 自己的 `hooks/hooks.json`——它被当作 ECC 受管的新文件整体写入（见 [第五节机制 2](#五安装过程中的特殊处理机制)），不是去 patch 用户既有配置。

## 二、执行链路（从命令到落盘）

```
install.sh
  │  ① 若 node_modules 不存在 → npm install（装依赖到仓库，非 ~/.claude/）
  └─exec node scripts/install-apply.js "$@"   （透传 --profile full 等参数）
       │
       install-apply.js  main()  [install-apply.js:137]
       │  ② parseInstallArgs(process.argv)        参数解析在 lib/install/request.js:17-85
       │  ③ normalizeInstallRequest(...)          request.js:87-151
       │  ④ createInstallPlanFromRequest(request) [install-apply.js:164] → runtime.js
       │       └─（manifest 模式）createManifestInstallPlan  [install-executor.js:722-804]
       │            └─ resolveInstallPlan 读 3 个 manifest：
       │                 manifests/install-modules.json
       │                 manifests/install-profiles.json
       │                 manifests/install-components.json（可选）
       │            └─ profile → module → 操作（adapter.planOperations 生成 copy-path）
       │  ⑤ applyInstallPlan(plan)  [install-apply.js:180 → 定义于 apply.js:226-346]
       │       复制文件、写 hooks.json、写 install-state.json
```

要点：
- **`install.sh` 只是个壳**（[install.sh](../install.sh)，33 行）：解析符号链接拿到真实仓库目录 → 首次运行自动 `npm install` → `exec node scripts/install-apply.js "$@"` 透传所有参数。本身不含任何安装逻辑。
- **`npm install` 触发条件**：`[ ! -d "$SCRIPT_DIR/node_modules" ]`（[install.sh:18](../install.sh#L18)）——只要仓库根没有 `node_modules/` 就装一次，装到**仓库内**（`--no-audit --no-fund`），不进 `~/.claude/`。原因见 [延伸 B](#延伸-b为什么先-npm-install)。
- **参数解析不在 install-apply.js 里**：`--profile/--target/--modules/--skills/--with/--without/--locale/--dry-run/--json` 的解析在 [lib/install/request.js:17-85](../scripts/lib/install/request.js#L17)；install-apply.js 只调用。
- **计划构建是间接调用**：install-apply.js 调的是 `createInstallPlanFromRequest`（[install-apply.js:153](../scripts/install-apply.js#L153) → [runtime.js](../scripts/lib/install/runtime.js)），它按 `request.mode` 分派，`manifest` 模式下才调到 `createManifestInstallPlan`（[install-executor.js:722](../scripts/lib/install-executor.js#L722)）。

## 三、路径映射规则（target=claude）

源路径到目标位置的映射**全部由一个函数决定**：[claude-home.js](../scripts/lib/install-targets/claude-home.js) 的 `getClaudeManagedDestinationPath`（L12-46）。规则如下：

| 源路径（仓库内） | 目标位置 | 规则出处 | 说明 |
|---|---|---|---|
| `rules/`、`rules/*` | `~/.claude/rules/ecc/...` | [claude-home.js:16-27](../scripts/lib/install-targets/claude-home.js#L16) | **加 `ecc/` 命名空间**（路径隔离，避免与用户自有 rules 冲突） |
| `skills/`、`skills/*` | `~/.claude/skills/<name>/...` | [claude-home.js:29-39](../scripts/lib/install-targets/claude-home.js#L29) | **扁平，不加 `ecc/`** ⭐ 与 rules 故意不对称 |
| `.claude-plugin/` | `~/.claude/`（提升到根） | [claude-home.js:54](../scripts/lib/install-targets/claude-home.js#L54)（`nativeRootRelativePath`） | 4 个文件散铺到 `~/.claude/` 根 |
| `docs/`、`docs/*` | `~/.claude/docs/...` | [claude-home.js:41-43](../scripts/lib/install-targets/claude-home.js#L41) | 仅 `--locale` 时纳入，`full` 不含 |
| 其它（`agents`、`commands`、`hooks`、`scripts/*`、`mcp-configs`、`AGENTS.md`、`.agents` 等） | `~/.claude/<原相对路径>` | [claude-home.js:45](../scripts/lib/install-targets/claude-home.js#L45) 返回 null → 默认原样拼接 | |
| 其它平台目录（见下） | **跳过** | [helpers.js:28-38](../scripts/lib/install-targets/helpers.js#L28) `isForeignPlatformPath` | target=claude 时不装 |

### ⭐ skills 为什么是扁平的（关键）

[claude-home.js:29-39](../scripts/lib/install-targets/claude-home.js#L29) 明确：`skills/<name>` 映射为 `path.join(targetRoot, 'skills', <name>)`，**没有 `ecc/` 中间层**。这与 `rules/`（拼 `ecc/`）是**刻意不对称**的设计——因为 Claude Code 只从 `~/.claude/skills/` 的**直接子目录**发现 skill（`<name>/SKILL.md`，不递归），所以 install.sh 必须扁平安装，skill 装完即可被识别使用。dry-run 实测交叉印证：**0 个目标路径含 `skills/ecc/`**。

> 旧版 ECC 曾把 skill 嵌套到 `skills/ecc/`，导致无法识别；现在的 installer 内建了**自动迁移**逻辑，会把旧版嵌套文件迁回扁平（见 [第五节机制 1](#1-扁平-skill-安装--旧版嵌套自动迁移)）。官方文档也明确建议手动安装不要嵌套：[README.md:358](../README.md#L358)、[README.md:454](../README.md#L454)。

### foreign 平台过滤名单（完整 13 项）

[helpers.js:5-19](../scripts/lib/install-targets/helpers.js#L5) 的 `PLATFORM_SOURCE_PATH_OWNERS`：

`.claude-plugin`(claude)、`.codex`、`.cursor`、`.gemini`、`.hermes`、`.kimi`/`.kimi-code`、`.joycode`、`.opencode`、`.openclaw`、`.codebuddy`、`.qwen`、`.zed`。

target=claude 时，除 `.claude-plugin`（owner 就是 claude，走 nativeRoot 提升、不过滤）外，其余平台目录一律被 [claude-home.js:68](../scripts/lib/install-targets/claude-home.js#L68) 的 `.filter(p => !isForeignPlatformPath(...))` 过滤掉。

## 五、安装过程中的特殊处理（机制）

apply 阶段（[apply.js:226-346](../scripts/lib/install/apply.js#L226) `applyInstallPlan`）不是单纯的逐文件复制，内含若干关键机制：

### 1. 扁平 skill 安装 + 旧版嵌套自动迁移

[apply.js:230](../scripts/lib/install/apply.js#L230) `prepareClaudeSkillMigration`、[apply.js:325-327](../scripts/lib/install/apply.js#L325) `removeLegacyClaudeSkillFiles`：

- 旧版 ECC 曾把 skill 装到嵌套的 `skills/ecc/`，新版改为扁平。installer 会把 install-state 里记录的旧嵌套文件**自动迁移/清理**为扁平结构。
- **用户自有的同名扁平 skill 不会被覆盖**：若 `~/.claude/skills/<name>/` 是用户自己放的，ECC 保留它、打印冲突警告，仅继续追踪自己旧的受管副本，以便安全卸载（对应 [README.md:358](../README.md#L358) 的描述）。
- 每个写操作前后都过 [apply.js:253/259](../scripts/lib/install/apply.js#L253) `assertSafeClaudeSkillOperation` 做 skill 专属安全校验。

### 2. hooks.json 整文件写 + 占位符机制

[apply.js:178-208](../scripts/lib/install/apply.js#L178) `buildResolvedClaudeHooks` + [apply.js:311-323](../scripts/lib/install/apply.js#L311)：

- hooks.json 先作为 1 条 copy-file 算进 1003 操作；apply 末尾再**额外整体重写** `~/.claude/hooks/hooks.json`（非 byte-for-byte）。
- 占位符替换函数 [replacePluginRootPlaceholders](../scripts/lib/install/apply.js#L108)（L108-131）会把字符串里的 `${CLAUDE_PLUGIN_ROOT}` 替换成 `~/.claude/`。
- **但当前的 [hooks/hooks.json](../hooks/hooks.json) 并不含字面 `${CLAUDE_PLUGIN_ROOT}` 占位符**——它内嵌的 `node -e` 脚本在**运行时**读 `process.env.CLAUDE_PLUGIN_ROOT`，读不到就走多候选 fallback 解析（遍历 `~/.claude/plugins/<ecc|ecc@ecc|...>` 等候选目录）。所以对当前 hooks.json，占位符替换实际是 no-op；真正让"同一份 hooks.json 适配插件/手动两种安装"的是这个 env+fallback 机制（[hooks.json:5-15](../hooks/hooks.json#L5)）。
- 这写的是 ECC 自己受管的新文件，不是去 patch 用户既有 hooks.json，故仍符合"不改已有配置"。

### 3. 安全闸门

[apply.js:146-176](../scripts/lib/install/apply.js#L146) `assertSafeInstallOperation`：每个操作写入前后都校验——

- `assertWithinTrustedRoot`：目标必须落在受信根 `~/.claude/` 内，防越界；
- **拒绝穿越符号链接的路径**（[apply.js:164-168](../scripts/lib/install/apply.js#L164)）：逐级 `lstatSync`，遇到 symlink 立即抛错，防 symlink 劫持。

### 4. Markdown 相对链接重写

[apply.js:294-306](../scripts/lib/install/apply.js#L294)：复制 markdown 时，若文档内有指向"被移动过的目标"（如 rules 被挪到 `rules/ecc/`）的相对链接，用 `rewriteRelativeLinks` 自动修正，保证 rules 文档里的相互链接不因目录变更而失效。非 markdown 文件走 byte-for-byte 的 `fs.copyFileSync`（[apply.js:308](../scripts/lib/install/apply.js#L308)）。

### 5. 内容指纹追踪

[apply.js:328](../scripts/lib/install/apply.js#L328) `stateWithContentDigests` 给每个操作算 `contentSha256` 写进 install-state。升级时据此判断文件是否变化、是否需要更新；卸载时据此精确回滚自己写入的文件。

## 六、明确不改动的内容（否定清单 + 依据）

| 项目 | 是否改动 | 依据 |

| 用户自有的同名扁平 skill | ❌ 不覆盖 | 迁移逻辑保留 + 警告（机制 1） |

## 延伸 A：与 `/plugin install ecc@ecc` 的对比

| 维度 | `/plugin install ecc@ecc`（插件） | `./install.sh --profile full`（手动） |
|---|---|---|
| **本质** | Claude Code 拉取 marketplace 仓库到**插件缓存**并引用 | **物理复制**文件到用户目录 |
| **安装位置** | `~/.claude/plugins/...`（Claude Code 托管） | 散落到 `~/.claude/` 各子目录 |
| **启用记录** | 写 `~/.claude/settings.json` 的 `enabledPlugins` 等 | 写 `~/.claude/ecc/install-state.json`（不动 settings.json） |
| **skills** | 全量 284（`plugin.json` 声明 `["./skills/"]`），`ecc:` 命名空间 | full 装 **283**（几乎全量）；放 `~/.claude/skills/<name>/`（扁平，无命名空间） |
| **commands** | 全量 94，`/ecc:xxx` 命名空间 | 全量 94，`/xxx`（无命名空间） |
| **agents** | 67，按约定自动发现（[PLUGIN_SCHEMA_NOTES.md:85](../.claude-plugin/PLUGIN_SCHEMA_NOTES.md#L85)） | 67，复制到 `~/.claude/agents/` |
| **hooks** | 自动加载 `hooks/hooks.json`（[PLUGIN_SCHEMA_NOTES.md:119](../.claude-plugin/PLUGIN_SCHEMA_NOTES.md#L119)），`CLAUDE_PLUGIN_ROOT` 由 Claude Code 注入 | 复制到 `~/.claude/hooks/`，靠 env+fallback 解析（同一份 hooks.json 两种解析路径） |
| **rules** | ❌ 不支持（Claude Code 插件系统不分发 rules） | ✅ 复制到 `~/.claude/rules/ecc/`（含 common + 各语言） |
| **MCP** | 显式 opt-out（`mcpServers: {}`，[plugin.json:39](../.claude-plugin/plugin.json#L39)，防工具名超 64 字符） | 复制 `mcp-configs/mcp-servers.json`（仅复制不激活） |
| **scripts/lib** | 不装（hook 从插件缓存根解析） | 复制到 `~/.claude/scripts/`（hook 运行时依赖） |
| **更新** | `/plugin marketplace update ecc` → `/plugin update` | `git pull` → 重跑 `./install.sh --profile full` |
| **卸载** | `/plugin uninstall ecc@ecc`（干净） | 跑 [uninstall.js](../scripts/uninstall.js)，读 install-state 回滚 |
| **跨 harness** | ❌ Claude Code 专属 | ✅ `--target cursor\|codex\|gemini\|opencode\|zed\|...` |
| **可裁剪** | 只能整体启用/禁用 | `--profile minimal\|core\|developer\|research\|security\|full`、`--modules`、`--skills`、`--with/--without` |

> **关于"手动=精选"**：这是个常见误解。`full` profile 实际装了 283/284 个 skill（近乎全量），并非精选。真正的精选能力体现在 `minimal`/`core` 等更小的 profile 和 `--modules`/`--skills` 参数上。

**⚠️ 两种方式不可叠加**：插件已自动加载 skills/commands/hooks，再跑 `install.sh --profile full` 会把同一批内容复制到用户目录，导致 skill 重名重复触发、hook 同事件跑两遍、`${CLAUDE_PLUGIN_ROOT}` 解析冲突。**二选一**（参见 [README.md:358](../README.md#L358)、[README.zh-CN.md:167](../README.zh-CN.md#L167)）。

**MCP 两种方式都不会自动启用**：需自己把 `mcp-configs/mcp-servers.json` 条目粘进 `~/.claude/settings.json` 或项目 `.mcp.json`，并填真实 API key。

**`multi-*` 命令两种方式都不含 `ccg-workflow` 运行时**：需额外 `npx ccg-workflow` 初始化（[README.zh-CN.md:205-213](../README.zh-CN.md#L205)）。

## 延伸 B：为什么先 npm install

**直接回答：是为安装过程自己能跑起来，不是为日常使用 ECC。**

[package.json](../package.json) 的运行时 `dependencies` 只有 **3 个**：`ajv`、`@iarna/toml`、`sql.js`（另有 8 个 `devDependencies` 如 eslint/c8/markdownlint-cli，仅开发期用）。其中 **`ajv` 是 installer 的硬门槛**：

| 包 | 安装过程用 | 日常使用（hooks/skills/commands）用 |
|---|---|---|
| `ajv` | ✅ 硬 require，校验 `ecc-install.json`（[config.js:5](../scripts/lib/install/config.js#L5)，schema = `schemas/ecc-install-config.schema.json`） | ❌ |
| `@iarna/toml` | 边缘（`--target codex` / Codex 同步：[codex/merge-codex-config.js:19](../scripts/codex/merge-codex-config.js#L19)） | ❌（control-pane/state.js 读 ecc2.toml 用到，属可选高级功能） |
| `sql.js` | ❌ | ❌（control-pane/state-store 的 SQLite 持久化，可选） |

**实证崩溃路径**：不装 ajv 时，`node install-apply.js` 在加载阶段就抛 `Cannot find module 'ajv'`——[install-apply.js:148](../scripts/install-apply.js#L148) `require('./lib/install/config')` → [config.js:5](../scripts/lib/install/config.js#L5) 顶层 `require('ajv')` 立即失败，尚未进入任何安装逻辑（无论是否传 `--config`）。

**两个关键事实：**

1. **日常 hooks 零第三方依赖**。对 `scripts/hooks/` 全量扫描，所有 `require` 都是相对路径（`../lib/utils`、`./bash-hook-dispatcher` 等）或 Node 内置模块——没有任何第三方包。PreToolUse/PostToolUse/Stop 这些每次工具调用触发的 hook，只靠 Node 内置 + 本地 `scripts/lib/`，装不装依赖不影响。

2. **`npm install` 只装在仓库目录，不进 `~/.claude/`**。[install.sh:20](../install.sh#L20) 的 `npm install` 在仓库根。手动安装只把 `scripts/lib/` 等**文件复制**到 `~/.claude/scripts/lib/`，**不复制 `node_modules`**。所以即便需要 `sql.js`/`toml` 的可选模块（state-store、control-pane）被复制过去了，`~/.claude/` 那边也找不到这些包——`npm install` 对"使用 ECC 时"在目标目录里帮不上忙。这些模块主要服务于**仓库内**场景（开发、CI、`npx ecc`、Codex 同步），不是手动安装后的日常 hook 链路。

**总结**：`npm install` 的真正作用是让 **installer 自己能跑起来**（`ajv` 是 `install-apply.js` 的硬前置），附带让仓库内的开发/CI/Codex 同步脚本可用；它**不是**日常使用 ECC（hooks、skills、commands）的前提。
