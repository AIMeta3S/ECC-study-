### Agent 编排策略

ECC 提供 60 个专业化 Agent，按职责分为以下几类：

#### 核心 Agent（6 个）

| Agent | 用途 | 触发条件 | 使用工具 | 推荐模型 |
|-------|------|---------|---------|---------|
| planner | 实现计划制定 | 复杂功能需求、架构变更、重构 | Read, Grep, Glob | Opus |
| code-reviewer | 代码质量审查 | 代码修改后自动触发 | Read, Grep, Glob, Bash | Sonnet |
| architect | 系统架构设计 | 新功能设计、技术决策、可扩展性规划 | Read, Grep, Glob | Opus |
| loop-operator | 自主循环监控与干预 | 运行自主代理循环时 | Read, Grep, Glob, Bash, Edit | Sonnet |
| security-reviewer | 安全漏洞检测 | 处理用户输入、认证、API 端点、敏感数据 | Read, Write, Edit, Bash, Grep, Glob | Sonnet |
| tdd-guide | TDD 强制执行 | 编写新功能、修复 Bug、重构 | Read, Write, Edit, Bash | Opus |

#### Agent 编排原则

ECC 方法论要求 **主动委托**（Proactive Delegation），不需要用户提示：

```
复杂功能 → planner
代码修改 → code-reviewer
Bug 修复 → tdd-guide
架构决策 → architect
安全相关 → security-reviewer
构建失败 → build-error-resolver
```

**关键约束**：reviewer 不应编写它审查的代码。每个阶段在自己的上下文窗口中运行，消除作者偏见。

| 环境变量 | 类型 | 默认值 | 说明 |

### Skill 开发模板

创建新 Skill 的标准格式（SKILL.md）：

```markdown
---
name: my-skill
description: 简要描述 Skill 的用途和触发条件
origin: ECC        # 或自定义来源
version: 1.0.0     # 可选
tools: [Read, Grep, Glob]  # 可选，列出所需工具
---

# Skill 标题

## When to Activate
- 触发条件 1
- 触发条件 2

## How It Works
详细的工作流程说明

## Examples
具体示例

## Anti-Patterns
- 反模式 1
```

**frontmatter 字段说明**：

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | Skill 唯一标识，小写连字符 |
| `description` | 是 | 用途描述，Claude 据此判断是否激活 |
| `origin` | 否 | 来源标识（ECC / 自定义） |
| `version` | 否 | 版本号 |
| `tools` | 否 | 声明所需工具列表 |

**Skill 放置策略**（参见 `docs/SKILL-PLACEMENT-POLICY.md`）：
- 策划维护的 Skill 放在 `skills/` 目录
- 生成/导入的 Skill 放在 `~/.claude/skills/`

## 高级用法

### 工作流编排

#### 场景一：TDD 完整开发流水线

将 tdd-workflow + verification-loop + code-reviewer 串联：

```
1. planner Agent → 分析需求，制定实现计划
2. tdd-workflow Skill → RED: 编写测试用例并验证失败
3. tdd-workflow Skill → GREEN: 编写最小实现使测试通过
4. verification-loop Skill → Build → TypeCheck → Lint → Test → Security → DiffReview
5. code-reviewer Agent → 代码质量审查（独立上下文窗口）
6. strategic-compact → 紧凑后进入下一功能
```

#### 场景二：自主循环模式

根据任务复杂度选择合适的循环架构：

```
单一聚焦变更？ ──── 是 ──→ Sequential Pipeline (claude -p)
                              │
                              否
                              │
有书面规范/RFC？ ──── 是 ──→ 需要并行实现？
                              │          │
                              │        是 → Ralphinho (DAG 编排)
                              │          │
                              │        否 → Continuous Claude (迭代 PR)
                              │
                              否
                              │
需要同一事物的多种变体？ ── 是 → Infinite Agentic Loop
                              │
                              否 → Sequential Pipeline + De-Sloppify
```

**Sequential Pipeline 示例**：

```bash
#!/bin/bash
set -e

# Step 1: 研究（Opus，深度推理）
claude -p --model opus "Analyze the codebase architecture and write a plan for adding caching..."

# Step 2: 实现（Sonnet，快速执行）
claude -p "Implement the caching layer according to the plan in docs/caching-plan.md..."

# Step 3: De-Sloppify（清理）
claude -p "Review all changes. Remove unnecessary type tests, overly defensive checks. Keep business logic tests."

# Step 4: 验证
claude -p "Run full build, lint, type check, and test suite. Fix any failures. No new features."

# Step 5: 提交
claude -p "Create a conventional commit for all staged changes."
```

#### 场景三：持续学习系统

基于 Hook 的自动学习流程：

```
会话活动（在 Git 仓库中）
      │
      │ Hooks 捕获 100% 的工具调用（PreToolUse/PostToolUse）
      │ + 检测项目上下文（git remote URL / 仓库路径）
      v
projects/<project-hash>/observations.jsonl
      │
      │ Observer Agent（后台，Haiku 模型）分析
      v
模式检测：
  - 用户修正 → 直觉
  - 错误解决方案 → 直觉
  - 重复工作流 → 直觉
      │
      │ 创建/更新
      v
projects/<hash>/instincts/personal/   ← 项目级直觉
instincts/personal/                    ← 全局直觉
      │
      │ /evolve 聚类 + /promote 提升
      v
evolved/ 目录 → 新 skills/commands/agents
```

**直觉置信度演化**：

| 分数 | 含义 | 行为 |
|------|------|------|
| 0.3 | 试探性 | 建议但不强制 |
| 0.5 | 中等 | 相关时应用 |
| 0.7 | 强 | 自动批准应用 |
| 0.9 | 近确定 | 核心行为 |

**自动提升条件**：同一直觉在 2+ 个项目中出现，且平均置信度 >= 0.8。

### 跨平台适配

#### Cursor DRY 适配器模式

Cursor 通过 `.cursor/hooks/adapter.js` 实现 Hook 复用：

```
Cursor stdin JSON → adapter.js → transformToClaude() → scripts/hooks/*.js（与 Claude Code 共享）
```

适配器核心逻辑（来自 `.cursor/hooks/adapter.js`）：
1. 读取 Cursor 的 stdin JSON
2. 将字段映射为 Claude Code 格式（tool_input, tool_output, transcript_path）
3. 委托给 `scripts/hooks/` 下已有的 Hook 脚本
4. 转发阻塞退出码（exit code 2）

#### OpenCode 配置

OpenCode 通过 `opencode.json` 声明所有 Agent、Skill、Command：

- 每个 Agent 明确声明 `mode`（primary/subagent）、`model`、`tools`
- 每个 Command 绑定到特定 Agent，设置 `subtask: true`
- Skills 通过 `skills.paths` 引用外部 Skill 目录

### 自定义 Skill 开发

#### 完整步骤

1. 创建 Skill 目录：`skills/my-skill/`
2. 编写 `SKILL.md`（使用上述模板）
3. 编写 Hook 脚本（如需要）：`skills/my-skill/hooks/observe.sh`
4. 编写辅助脚本：`skills/my-skill/scripts/`
5. 测试：在 `tests/` 中添加对应测试

#### 最佳实践

- **单一职责**：每个 Skill 只解决一个问题
- **声明式触发**：description 中清晰描述触发条件
- **渐进增强**：从简单开始，按需增加复杂度
- **测试覆盖**：新 Skill 应有对应的测试文件

## 集成方案

### 与 Claude Code 集成（推荐）

```bash
# 方法一：插件安装（推荐）
/plugin marketplace add https://github.com/affaan-m/ECC
/plugin install ecc@ecc

# 方法二：npm 安装
npm install ecc-universal

# 方法三：Shell 安装器
./install.sh --profile full --target claude

# 方法四：npx 安装
npx ecc-install --profile full --target claude
```

**注意事项**：
- 不要叠加多种安装方法（如 plugin + 手动安装器）
- Rules 不会自动分发，需手动复制：`cp -R rules/<category> ~/.claude/rules/ecc/`
- 可用 Rules 类别：common, typescript, python, golang, swift, php, rust, java, kotlin 等 19 种

```bash
./install.sh --profile full --target cursor
```

Cursor 安装后：
- Rules、Hooks、配置自动部署到 `.cursor/`
- Hook 通过 DRY 适配器模式复用 `scripts/hooks/` 下的脚本
- 15 个 Hook 事件通过 `adapter.js` 转换格式


Codex 限制：无 Hook 执行等价功能，通过 `AGENTS.md` 指令层补偿。

### MCP 服务器集成

ECC 预配置 28 个 MCP 服务器。常用集成：

| MCP 服务器 | 用途 | 对应 Skill |
|-----------|------|-----------|
| firecrawl | 网页抓取和搜索 | deep-research |

### 自定义 Hook 开发

Hook 脚本遵循以下规范（来自项目 Node.js 规则）：

```
- 通过 stdin 接收 JSON 数据
- CommonJS 格式（require/module.exports）
- 所有 Hook 必须 exit 0 处理非关键错误（永远不要意外阻塞工具执行）
- 阻塞型 Hook（PreToolUse, Stop）保持在 200ms 内
- 使用 run-with-flags.js 包装器以支持 ECC_HOOK_PROFILE 和 ECC_DISABLED_HOOKS
- 日志输出到 stderr，使用 [HookName] 前缀
- Hook 脚本保持在 200 行以内，辅助函数提取到 scripts/lib/
```

## 故障排查

### 排查决策树

```
问题现象
  ├─ Skill 未触发
  │    ├─ 检查 SKILL.md 的 description 是否匹配当前场景
  │    │    └─ description 中的关键词决定了触发概率
  │    ├─ 检查 Skill 是否在正确路径（~/.claude/skills/ 或插件目录）
  │    │    └─ 策划 Skill 在 skills/，导入 Skill 在 ~/.claude/skills/
  │    └─ 检查是否有多个 Skill 竞争同一触发条件
  │         └─ Claude 根据 description 相关度选择
  │
  ├─ Hook 未执行
  │    ├─ 检查 ECC_HOOK_PROFILE 是否正确
  │    │    └─ minimal 只包含基础 Hook，standard 和 strict 包含更多
  │    ├─ 检查 ECC_DISABLED_HOOKS 是否禁用了目标 Hook
  │    │    └─ 值为逗号分隔的 Hook ID
  │    ├─ 检查 plugin-hook-bootstrap.js 是否能找到 CLAUDE_PLUGIN_ROOT
  │    │    └─ 搜索路径：env var → ~/.claude → plugins/ 子目录 → cache/
  │    └─ 检查 Hook 脚本路径是否正确
  │         └─ 所有 Hook 使用 run-with-flags.js 包装器
  │
  ├─ 平台不兼容
  │    ├─ 检查目标平台的 Hook 支持情况
  │    │    └─ Codex: 无 Hook → 通过 AGENTS.md 指令补偿
  │    │    └─ Gemini: 仅 Rules → 无 Agent/Skill/Hook
  │    ├─ 检查安装方式是否与平台匹配
  │    │    └─ 不要叠加多种安装方法
  │    └─ 检查适配器版本是否最新
  │         └─ Cursor: adapter.js 版本需与 scripts/hooks/ 兼容
  │
  ├─ 安装失败
  │    ├─ 检查 Node.js 版本 >= 18
  │    ├─ 检查是否混用了安装方法
  │    │    └─ plugin install 和手动安装不应同时使用
  │    └─ 使用诊断命令
  │         └─ node scripts/ecc.js doctor
  │         └─ node scripts/ecc.js list-installed
  │
  ├─ 持续学习不工作
  │    ├─ 检查 observe.sh 是否注册（插件安装自动注册）
  │    ├─ 检查数据目录权限
  │    │    └─ ${XDG_DATA_HOME:-~/.local/share}/ecc-homunculus/
  │    ├─ 检查 observer.enabled 配置（默认 false）
  │    │    └─ 在 config.json 中设置 observer.enabled: true
  │    └─ 检查是否有 git 仓库（项目检测依赖 git remote）
  │
  └─ 上下文耗尽/性能下降
       ├─ 检查加载的 Skill 数量（每个 1-5K Token）
       ├─ 检查 MCP 服务器数量（每个消耗上下文）
       ├─ 使用 strategic-compact 在逻辑边界压缩
       │    └─ 研究完成后 → 压缩
       │    └─ 实现计划写入文件后 → 压缩
       │    └─ 调试完成后 → 压缩
       └─ 使用 /clear 在任务切换时清理
```

### 常见错误及解决

| 错误信息 | 原因 | 解决方法 |
|----------|------|----------|
| `[HookName] WARNING: could not resolve ECC plugin root` | plugin-hook-bootstrap.js 找不到插件根目录 | 确认安装路径正确，或设置 `CLAUDE_PLUGIN_ROOT` 环境变量 |
| Hook 双重执行 | 插件安装 + 手动 settings.json 同时注册了同一 Hook | 移除 settings.json 中的手动注册，只保留插件 Hook |
| `ECC_HOOK_PROFILE` 无效 | 值不是 minimal/standard/strict 之一 | 使用有效值，无效值回退到 standard |
| Skill 描述不触发 | description 中的关键词不匹配当前场景 | 修改 description，添加更多触发关键词 |
| Codex 下 Hook 不执行 | Codex 不支持 Hook 机制 | 通过 AGENTS.md 指令层实现等价功能 |
| 直觉数据未生成 | observer.enabled 默认为 false | 在 config.json 中启用，或等待足够观察量（默认 20 条） |

## 最佳实践

### 推荐做法

- **使用 search-first 而非直接编码**：在实现新功能前，先用 search-first 检查现有方案，避免重复造轮子。来源：`skills/search-first/SKILL.md`

- **主动委托 Agent**：不需要等用户指令，复杂功能委托 planner，代码修改后委托 code-reviewer，安全相关委托 security-reviewer。来源：`skills/continuous-learning-v2/SKILL.md` 方法论

- **使用 De-Sloppify 模式**：在自主循环中，用独立的清理代理替代负面指令（"不要做 X"），两个专注的代理优于一个受限的代理。来源：`skills/autonomous-loops/SKILL.md`

- **在逻辑边界压缩上下文**：研究完成后、计划写入文件后、调试完成后执行 `/compact`，而非等到自动压缩。来源：`skills/strategic-compact/SKILL.md`

- **使用 SHARED_TASK_NOTES.md 桥接上下文**：在连续 `claude -p` 调用间通过文件传递进度和下一步，弥补每次调用独立的上下文窗口。来源：`skills/autonomous-loops/SKILL.md`

- **默认使用 Sonnet 模型**：仅在深度架构推理时切换到 Opus。使用 `/clear` 在任务间切换，`/compact` 在断点处压缩。来源：`methodology.json` token 优化原则

- **项目级直觉隔离**：React 模式留在 React 项目，Python 约定留在 Python 项目，通用模式（如"始终验证输入"）全局共享。来源：`skills/continuous-learning-v2/SKILL.md`

### 反模式警告

- **不要叠加多种安装方法**：plugin install + 手动安装器会导致 Hook 双重执行和 `${CLAUDE_PLUGIN_ROOT}` 解析错误

- **不要同时启用所有 MCP 服务器**：每个 MCP 服务器消耗上下文窗口 Token，按需启用

- **不要使用负面指令替代清理步骤**：在实现步骤中添加"不要做 X"会让模型对所有相关行为变得犹豫；应添加独立的 De-Sloppify 清理步骤

- **不要让 reviewer 审查自己写的代码**：每个审查阶段应在独立的上下文窗口中运行，消除作者偏见

- **不要跳过 RED 阶段**：测试必须先运行并失败（编译+执行，不仅仅是编写），然后才能编写实现代码

- **不要在无限循环中缺少退出条件**：始终设置 max-runs、max-cost、max-duration 或完成信号

- **不要忽略工具可用性预检**：在 search-first 工作流中，先检查搜索渠道是否可用，不可用时诚实报告

## 性能优化

### 针对 Token 消耗的优化

| 优化手段 | 效果 | 适用条件 | 实施方法 |
|---------|------|---------|---------|
| Trigger-Table 懒加载 | 基线上下文减少 50%+ | 会话开始时 | 使用触发词表按需加载 Skill，而非全量加载 |
| 模型路由 | 成本降低 4-19x | 批处理场景 | 简单任务用 Haiku，复杂任务用 Sonnet/Opus |
| Prompt Caching | 重复请求成本降低 | 系统提示 > 1024 Token | 在 messages 中使用 cache_control |
| strategic-compact | 避免上下文溢出 | 长会话 | 在逻辑边界执行 /compact |
| MCP 按需启用 | 减少基线上下文 | 多 MCP 场景 | 只启用当前任务需要的 MCP 服务器 |

### 针对 Hook 开销的优化

| 优化手段 | 效果 | 适用条件 | 实施方法 |
|---------|------|---------|---------|
| minimal profile | 最少 Hook 执行 | CI/CD 场景 | 设置 `ECC_HOOK_PROFILE=minimal` |
| 禁用特定 Hook | 精确控制 | 调试/性能调优 | 设置 `ECC_DISABLED_HOOKS=hook1,hook2` |
| async Hook | 非阻塞执行 | 不需要即时反馈的 Hook | 在 hooks.json 中设置 `"async": true` |

1. `CLAUDE_PLUGIN_ROOT` 环境变量（最高优先级）
2. `~/.claude/` 目录
3. `~/.claude/plugins/ecc` 等已知插件路径
4. `~/.claude/plugins/cache/` 缓存目录
