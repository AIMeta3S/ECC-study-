# Growth Log 技能

> **问题所在：**大多数人把"修了 X 里的一个 bug"当作学习日志来写。那是日记条目，不是学习产物。真正的 growth log 会提取出*模式*，让你下次能识别它。
>
> **本技能教授：**如何编写能跨 session 复利积累的学习条目。适用于任何笔记系统——Markdown 文件、Notion、Obsidian、纯文本。模板是通用的，可根据你的设置进行调整。

## 何时激活

- 完成复杂任务后（多文件、新功能、架构变更）
- 遭遇失败、失误，或出现"这比预期更难"的时刻后
- 当你想回顾一段时间内所学内容时

**不应激活的情况：**琐碎变更（修复拼写错误、单行微调、无需 debug 的配置值变更）。判断 threshold：*这个任务是否涉及 debug、返工、rollback 或非显而易见的决策？*如果是 → 写一条条目。如果否 → 跳过。

## 三条规则

### 规则 1：失败 > 成就

失败的养分密度高于成功。一个花了 2 小时才找到的 bug 所教的，比 3 个一次就成的功能更多。

**反面：**"成功实现了登录流程。"
**正面（web 开发）：**"登录流程：session token 未能持久化，因为在 Chrome 128+ 中 cookie 的 `SameSite` 默认值为 `Lax`。模式：跨 origin 时始终显式设置 `SameSite=None; Secure`。识别信号：在浏览器升级后或跨越 origin 边界时认证失效。"
**正面（data pipeline）：**"CSV 导入在空行上静默失败，因为 `pandas.read_csv(dropna=False)` 会保留零宽行，而 `len()` 会将其计为有效行。模式：在行数校验之前始终执行 `df.dropna(how='all', inplace=True)`。"

### 规则 2：伯乐原则（Bole Principle）

在编写新条目之前，先问自己：*"这在本质上是否与我已记录的某些内容相同？"*

相同的根因，不同的症状 → **合并**，而非重复记录。新的根因 → 新条目。

**如何检查：**在编写之前，用根因中的关键词搜索现有条目。如果找到匹配项，将新症状作为附加示例添加到现有条目下，而不是创建重复条目。

**示例：**"创建文件后忘记更新输出索引"和"任务完成后忘记更新 skill 评分"——相同的根因（没有自动捕获 trigger）。合并到一条关于"任务后捕获缺口"的条目中。

### 规则 3：必须可迁移

每条条目都必须回答：*"下次遇到类似情况时，我会采取什么不同的做法？"*

如果你写不出这句话，说明你还没有提取出模式。

**如何从具体事件中提取模式：**
1. 用一句话描述发生了什么
2. 迭代追问"为什么？"直到找到根因（通常需要 3-5 个为什么）
3. 泛化："这是哪一类问题？"（不是"Chrome 128 bug"，而是"浏览器默认值变更破坏现有行为"）
4. 表述为："下次看到[信号]时，我将[行动]。"
5. 命名信号：什么具体的可观测现象告诉你这个模式正在起作用？

## 条目模板

**范围：**每个不同的根因对应一条条目。典型长度：4-8 个句子。如果编写耗时 >2 分钟，说明你在叙述事件。如果 <30 秒，说明你挖掘得不够深。

```markdown
## [标题：模式，而非事件]

### 背景
- 我当时想做什么？
- 哪里出了问题 / 哪里出乎意料地顺利？

### 根因 / 核心洞察
- 底层机制，而不仅仅是症状

### 模式（可迁移）
- 下次[类似情况]，我将[具体行动]。
- 识别信号：[什么可观测现象告诉我这个模式正在起作用？]

### 相关
- [条目名](../path/to/related-entry.md)
```

## 条目类型

以上四种类型都使用上面的模板。类型决定了哪些部分权重最大：

| 类型 | 何时使用 | 重点 | 示例标题 |
|------|----------|------|----------|
| **失败** | 某些东西坏了、需要 debug 或需要返工 | 根因 | "配置继承 ≠ 跨 session 的行为继承" |
| **方法论** | 从工作中提炼出可重复的流程 | 背景 / 模式 | "PPT → 开卷考试学习指南：三层结构" |
| **模式发现** | 关于工具、系统或思维的可复用洞察 | 模式部分 | "PR description 模板：描述差距，而非功能" |
| **能力变化** | 可衡量的技能提升 | 背景（之前 vs 之后） | "Git：从 clone/push 到独立提交含 12 个 commit 的 PR" |

## 质量检查清单

在最终确定 growth log 条目之前：

- [ ] 标题命名的是*模式*，而非事件吗？
- [ ] 是否有一句"下次我将……"？
- [ ] "识别信号"是否足够具体，能在下次触发该模式？
- [ ] 编写之前是否搜索了现有条目以避免重复？（伯乐原则）
- [ ] 根因是否与症状区分开来？
- [ ] 相关记忆是否已相互交叉链接？
- [ ] 条目是否为 4-8 个句子？更短 = 太浅；更长 = 在叙述事件。

## 反模式

- 避免："修复了支付模块中的 bug"（事件，而非模式）
- 避免：逐字复制 git commit message（commit 描述了发生了什么变化；log 提取的是为什么重要）
- 避免：为每个 commit 都写一条条目（仅在出现模式时才写）
- 避免：跳过可迁移的句子（没有它，就只是日记——这一点不可妥协）
- 避免：在不同标题下重复同一个模式（违反伯乐原则——编写前先搜索）

## 存储

将条目存储在你保存笔记的任何地方。常见做法：
- `growth-log/` 目录中的 Markdown 文件（每天一个文件：`YYYY-MM-DD.md`）
- Notion、Obsidian 或你的笔记应用中的专属分区
- 具有一致命名约定的纯文本文件

选择一种约定并坚持下去。可搜索性比格式更重要。

## 如果你使用 Delivery Gate

`delivery-gate` 的 Stop hook 会通过文件系统时间戳检查学习文件今天是否被修改过。本技能教授*写什么*——这样 delivery-gate 检查的文件才真正包含有用的模式，而非空的时间戳。

```
任务完成 → delivery-gate 检查：今天是否修改过学习文件？
  → 过期（无文件修改）：block — "你学到了什么？"
  → 新鲜（文件已修改）：pass — 本技能确保内容有用
```

有强制机制而无方法论 → 空条目。有方法论而无强制机制 → 被遗忘的记录。两者各自独立都有用；两者结合才能形成闭环。
