# 财务计费运营

当用户想了解资金、定价、refund、团队席位逻辑，或产品实际行为是否与网站和销售文案所暗示的一致时，使用本 skill。

本 skill 的范围比 `customer-billing-ops` 更广。那个 skill 用于客户补救。本 skill 用于运营者真相：收入状态、定价决策、团队计费，以及有代码支撑的计费行为。

## Skill 栈

当相关时，将以下 ECC 原生 skill 拉入工作流：

- `customer-billing-ops` 用于针对具体客户的补救与跟进
- `research-ops` 当竞品定价或当前市场证据很重要时
- `market-research` 当答案应以定价建议收尾时
- `github-ops` 当计费真相依赖于兄弟仓库中的代码、backlog 或发布状态时
- `verification-loop` 当答案依赖于验证 checkout、席位处理或 entitlement 行为时

## 何时使用

- 用户询问 Stripe 销售、refund、MRR 或最近的客户活动
- 用户询问团队计费、per-seat billing 或配额叠加在代码中是否真实存在
- 用户想要竞品定价对比或定价模型基准
- 问题将收入事实与产品实现真相混在一起

## 护栏

- 区分实时数据与已保存的快照
- 分离以下内容：
  - 收入事实
  - 客户影响
  - 有代码支撑的产品真相
  - 建议
- 除非实际的 entitlement 路径强制执行，否则不要说 "per seat"
- 不要假设重复的 subscription 意味着重复的价值

## 工作流

### 1. 从最新的计费证据开始

优先使用实时计费数据。如果数据不是实时的，明确说明快照时间戳。

梳理全貌：

- 已付款销售
- 活跃 subscription
- 失败或不完整的 checkout
- refund
- dispute
- 重复的 subscription

### 2. 将客户事件与产品真相分开

如果问题是针对具体客户的，先进行分类：

- 重复 checkout
- 真实的团队意图
- 损坏的自助服务控件
- 未实现的产品价值
- 失败的支付或不完整的设置

然后将其与更广泛的产品问题分开：

- 团队计费是否真的存在？
- 席位是否真的被计数？
- checkout 数量是否会改变 entitlement？
- 网站是否夸大了当前行为？

### 3. 检查有代码支撑的计费行为

如果答案依赖于实现真相，检查代码路径：

- checkout
- 定价页面
- entitlement 计算
- 席位或配额处理
- 安装与用户使用逻辑的对比
- 计费门户或自助管理支持

### 4. 以决策和产品缺口收尾

报告：

- 销售快照
- 问题诊断
- 产品真相
- 建议的运营者行动
- 产品或 backlog 缺口

## 输出格式

```text
快照
- 时间戳
- 收入 / subscription / 异常

客户影响
- 受影响的人群
- 发生了什么

产品真相
- 代码实际做了什么
- 网站或销售文案声称什么

决策
- refund / 保留 / 转换 / no-op

产品缺口
- 需要构建或修复的具体后续事项
```

## 陷阱

- 不要将失败尝试与净收入混为一谈
- 不要仅凭营销语言推断团队计费
- 当有当前证据可用时，不要凭记忆对比竞品定价
- 不要在未对问题进行分类的情况下就从诊断直接跳到 refund

## 验证

- 答案包含实时数据声明或快照时间戳
- 产品真相声明有代码支撑
- 客户影响与更广泛的定价/产品结论被清晰地分开
