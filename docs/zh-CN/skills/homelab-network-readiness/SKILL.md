# Homelab 网络就绪检查

在变更混合使用 VLAN、Pi-hole 或其他本地 DNS 解析器、防火墙规则以及远程 VPN 访问的家庭或小型实验室网络之前，使用此 skill。

这是一个规划与审查 skill。除非目标平台、当前拓扑、回滚路径、console 访问方式以及维护窗口均已明确，否则不要将其变成可直接复制粘贴的路由器、防火墙或 VPN 配置。

## 何时使用

- 准备将扁平网络划分为受信任、IoT、访客、服务器或管理 VLAN。
- 将 DHCP 客户端迁移到 Pi-hole、AdGuard Home、Unbound 或其他本地 DNS 解析器。
- 添加 WireGuard、Tailscale、ZeroTier、OpenVPN 或路由器原生的 VPN 访问。
- 审查某项 homelab 变更是否会致使运维者无法访问网关、交换机、AP、DNS 服务器或 VPN 服务器。
- 将一个非正式的家庭网络想法转化为带有验证证据的分阶段迁移计划。

## 安全规则

- 首次回复保持只读：清单、风险、分阶段计划、验证和回滚。
- 不要将网关管理面板、DNS 解析器、SSH、NAS 控制台或 VPN 管理界面直接暴露到公网。
- 在没有确认平台和回滚流程的情况下，不要提供防火墙、NAT、VLAN、DHCP 或 VPN 命令。
- 在变更管理 VLAN、trunk 端口、防火墙默认策略或 DHCP/DNS 设置之前，要求具备带外或同房间的 console 访问条件。
- 在将整个网络指向新的 DNS 解析器或 VPN 路由之前，保留一条可用的返回互联网的路径。
- 在运维者明确作出其他选择之前，将 IoT、访客、摄像头和实验室服务器网络视为不同的信任区。

## 必备清单

在给出实施步骤之前，先收集以下信息：

| 方面 | 问题 |
| --- | --- |
| 互联网边缘 | modem 或 ONT 是什么？ISP 路由器是桥接还是仍在做路由？ |
| 网关 | 哪个设备负责路由、防火墙、处理 DHCP 并终结 VPN？ |
| 交换层 | 哪些交换机端口是 uplink、access 端口、trunk 端口或非网管端口？ |
| Wi-Fi | 哪些 SSID 映射到哪些网络，AP 是有线还是 mesh 组网？ |
| 地址规划 | 当前存在哪些子网，哪些地址范围与 VPN 站点冲突？ |
| DNS/DHCP | 当前由哪个服务分发租约和解析器地址？ |
| 管理 | 变更后运维者如何访问网关、交换机和 AP？ |
| 恢复 | 如果 DNS、DHCP、VLAN 或 VPN 路由故障，可以在本地回滚哪些内容？ |

## VLAN 与信任区规划

从意图出发，而非厂商语法。

| 区域 | 典型内容 | 默认策略 |
| --- | --- | --- |
| 受信任 | 笔记本、手机、管理工作站 | 仅在需要时才能访问共享服务和管理网络 |
| 服务器 | NAS、Home Assistant、实验室主机、DNS 解析器 | 接受来自受信任客户端的窄范围入站流量 |
| IoT | 电视、智能插座、摄像头、音箱 | 仅允许访问互联网以及明确的例外 |
| 访客 | 访客设备 | 仅可访问互联网，不可触达 LAN |
| 管理 | 网关、交换机、AP、控制器 | 仅可从受信任的管理设备访问 |
| VPN | 远程客户端 | 与受信任客户端相同或更窄的访问权限 |

在推荐 VLAN ID 或子网之前，确认：

1. 网关支持 VLAN 间路由和防火墙规则。
2. 交换机支持所需的 tagged 和 untagged 端口行为。
3. AP 能将 SSID 映射到 VLAN。
4. 运维者知道在变更期间自己通过哪个端口连接。
5. 在 trunk 和 SSID 变更之后，管理网络仍可访问。

## DNS 过滤就绪检查

应以依赖项的形式引入 Pi-hole 或其他本地解析器，而不是作为单点故障。

1. 在 DHCP 选项中使用解析器之前，先为其分配保留地址。
2. 确认它能解析公网 DNS 和本地 `home.arpa` 名称。
3. 保留网关或第二个解析器作为临时 fallback。
4. 在更改每个 DHCP 作用域之前，先测试一个客户端或一个 VLAN。
5. 记录哪些网络可以绕过过滤以及原因。
6. 检查拦截规则不会破坏强制门户、工作 VPN、固件更新或医疗/安防设备。

有用的验证证据：

```text
客户端获得预期的 DHCP 租约
客户端收到预期的 DNS 解析器
公网 DNS 查询成功
本地 home.arpa 查询成功
被拦截的测试域名仅在预期位置被拦截
从访客或 IoT 网络无法访问网关和 DNS 管理界面
```

## 远程访问就绪检查

对于 WireGuard 风格的访问，在生成密钥或开放端口之前，先决定 VPN 允许访问哪些资源。

| 模式 | 适用场景 | 风险说明 |
| --- | --- | --- |
| 单子网 split tunnel | 对 NAS 或实验室主机进行远程管理 | 保持路由列表范围窄 |
| 受信任服务的 split tunnel | 通过 IP 或 DNS 访问选定的应用 | 需要精确的防火墙规则 |
| Full tunnel | 不受信任的网络或出行场景 | 带宽和 DNS 责任更大 |
| Overlay VPN | 带有身份控制的更简单的远程访问 | 仍需要 ACL 审查 |

在运维者确认以下事项之前，不要推荐端口转发：

- VPN 端点已打补丁并处于积极维护中。
- 转发的端口仅指向 VPN 服务，而非管理 UI。
- 已了解动态 DNS、公网 IP 行为以及 ISP 的 CGNAT 状态。
- 可以在不重建整个网络的情况下吊销 peer key。
- 日志或连接状态能够验证谁在何时连接。

## 变更顺序

优先采用小型、可逆的变更：

1. 对当前拓扑、IP 规划、DHCP 设置、DNS 设置和防火墙规则做快照。
2. 为网关、DNS、控制器、AP、NAS 和 VPN 端点预留基础设施地址。
3. 在未移动关键设备的情况下创建新的区域或 VLAN。
4. 移动一个测试客户端，并验证 DHCP、DNS、路由、互联网和拦截行为。
5. 为所需的流量添加窄范围的防火墙例外。
6. 移动一个低风险设备组。
7. 在满足用例的前提下，添加范围最窄的路由和防火墙策略的 VPN 访问。
8. 记录最终状态、已知例外以及回滚命令或 UI 步骤。

## 审查清单

- 每个网络都有其存在的理由和清晰的信任边界。
- 任何管理界面都不能从访客、IoT 或公网访问。
- DNS 故障不会削弱运维者在本地恢复的能力。
- DHCP 作用域变更在广泛推行之前已在一个客户端上测试。
- VPN 客户端只接收所需的路由和 DNS 设置。
- 区域之间的防火墙规则为默认拒绝，并带有具名例外。
- 运维者仍能访问网关、交换机、AP、DNS 和 VPN 管理界面。
- 回滚以与所选平台 UI 或 CLI 相同的词汇记录。

## 反模式

- 在不知道哪些交换机端口和 SSID 承载哪些 VLAN 之前就划分网络。
- 将管理工作站移出唯一可访问的管理网络。
- 在测试 fallback DNS 之前就将所有 DHCP 作用域指向 Pi-hole。
- 将 NAS、DNS、路由器或 hypervisor 管理界面直接发布到互联网。
- 将 VPN 访问等同于完整的受信任 LAN 访问。
- 临时添加允许全部的防火墙规则并且忘记移除。
- 在不核对确切平台语法的情况下，从其他厂商或固件版本复制命令。
