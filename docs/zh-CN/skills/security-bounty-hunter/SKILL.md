# Security Bounty Hunter

当目标是面向负责任披露或赏金提交的实用漏洞发现，而非宽泛的最佳实践审查时，使用本 skill。

## 何时使用

- 扫描代码仓库以发现可利用的漏洞
- 准备 Huntr、HackerOne 或类似平台的赏金提交
- 分诊筛选时关注"这真的能拿到赏金吗？"而非"这在理论上不安全吗？"

## 工作原理

偏向于可远程触达、用户可控的攻击路径，丢弃那些被平台惯例性判定为信息性或超出范围的漏洞模式。

## 范围内的模式

这些是持续重要的漏洞类型：

| 模式 | CWE | 典型影响 |
| --- | --- | --- |
| 通过用户可控 URL 触发的 SSRF | CWE-918 | 内网访问、云元数据窃取 |
| 中间件或 API guard 中的认证绕过 | CWE-287 | 未授权的账户或数据访问 |
| 远程反序列化或上传导致 RCE 的路径 | CWE-502 | 代码执行 |
| 可触达端点中的 SQL 注入 | CWE-89 | 数据外泄、认证绕过、数据破坏 |
| 请求处理程序中的命令注入 | CWE-78 | 代码执行 |
| 文件服务路径中的路径遍历 | CWE-22 | 任意文件读取或写入 |
| 自动触发的 XSS | CWE-79 | 会话窃取、管理员账号失陷 |

## 跳过这些

这些通常是低信号或超出赏金范围的，除非赏金计划另有说明：

- 仅本地的 `pickle.loads`、`torch.load` 或等效调用，且无远程路径
- 仅用于 CLI 工具的 `eval()` 或 `exec()`
- 完全硬编码命令上的 `shell=True`
- 单纯缺失安全 header
- 没有利用影响的通用限速抱怨
- 需要受害者手动粘贴代码的 Self-XSS
- 不属于目标赏金计划范围的 CI/CD 注入
- Demo、示例或仅测试代码

## 工作流程

1. 先检查范围：赏金计划规则、SECURITY.md、披露渠道和排除项。
2. 寻找真实的 entrypoint：HTTP 处理程序、上传、后台作业、webhook、解析器和集成端点。
3. 在有帮助的地方运行静态工具，但仅将其视为分诊输入。
4. 端到端地阅读真实代码路径。
5. 证明用户可控输入能触达有意义的 sink。
6. 用尽可能最小的安全 PoC 确认可利用性和影响。
7. 在起草报告前检查重复。

## 示例分诊循环

```bash
semgrep --config=auto --severity=ERROR --severity=WARNING --json
```

然后手动筛选：

- 丢弃测试、demo、fixture、vendored 代码
- 丢弃仅本地或不可触达的路径
- 仅保留具有明确网络或用户可控路径的发现

## 报告结构

```markdown
## Description
[漏洞是什么以及为什么重要]

## Vulnerable Code
[文件路径、行范围和小段代码片段]

## Proof of Concept
[最小可用的请求或脚本]

## Impact
[攻击者能实现什么]

## Affected Version
[测试的版本、commit 或部署目标]
```

## Quality Gate

提交前：

- 代码路径可从真实用户或网络边界触达
- 输入确实是用户可控的
- sink 是有意义的且可利用的
- PoC 有效
- 该 issue 未被 advisory、CVE 或未解决的 ticket 覆盖
- 目标确实在赏金计划范围内
