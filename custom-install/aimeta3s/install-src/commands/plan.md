# Plan Command

此命令会在编写任何代码之前创建一份全面的实现计划。它接受自由格式的需求或 PRD markdown 文件。

默认以内联方式运行。默认不要调用 Task tool 或任何 subagent。这样可确保 `/plan` 在未附带 agent 文件的插件安装中也能直接使用。

## 该命令做什么

1. **重申需求** - 明确需要构建什么
2. **识别风险** - 揭示潜在问题和阻塞点
3. **制定分步计划** - 将实施方案分解为多个阶段。
4. **等待确认** - 必须收到用户批准才能继续

## 何时使用

在以下场景使用 `/plan`：
- 开始一个新功能
- 进行重大架构变更
- 处理复杂重构
- 将影响多个文件/组件
- 需求不清晰或存在歧义

## 如何工作

AI 将会：

1. **分析请求**并以清晰的术语重申需求
2. **将计划建立在相关代码库模式的基础上**（当仓库可用时）
3. **拆分为若干阶段**，包含具体、可执行的步骤
4. **识别组件之间的依赖关系**
5. **评估风险**和潜在阻塞点
6. **估算复杂度**（高/中/低）
7. **呈现计划**并等待你的明确确认

## 输入模式

| 输入 | 模式 | 行为 |
|---|---|---|
| `path/to/name.prd.md` | PRD 制品模式 | 读取 PRD，选取下一个待处理交付里程碑或实施阶段，并写入 `.claude/plans/{name}.plan.md` |
| 任何其他 markdown 路径 | 参考模式 | 将文件作为上下文读取，并直接在对话中生成计划 |
| 自由格式文本 | 对话模式 | 直接在对话中生成计划 |
| 空输入 | 澄清模式 | 询问需要计划什么 |

在 PRD 制品模式 下，如有需要则创建 `.claude/plans/`。如果 PRD 包含 `Delivery Milestones` 表，只将所选行从 `pending` 更新为 `in-progress`，并将其 `Plan` 单元格设置为生成的计划路径。如果 PRD 使用的是旧版 `.claude/PRPs/prds/` 格式且包含 `Implementation Phases`，则直接读取，不迁移路径。

## 模式依据

在编写计划之前，先在代码库中搜索需要遵循的实现规范。针对每个相关类别，找到最佳示例并附上文件引用：

| 类别 | 捕获内容 |
|---|---|
| 命名 | 受影响区域内的文件、函数、类型、命令或脚本命名 |
| 错误处理 | 失败是如何被抛出、返回、记录或被优雅处理的 |
| 日志 | 日志级别、格式以及记录哪些内容 |
| 数据访问 | Repository、service、query 或 filesystem 模式 |
| 测试模式 | 测试文件位置、框架、fixtures 和 assertion 风格 |

如果不存在相似代码，应明确说明，不要臆造模式。

## PRD 制品输出

当使用 `.prd.md` 文件调用时，将计划写入 `.claude/plans/{kebab-case-name}.plan.md`，使用如下结构：

````markdown
# 计划：{功能名称}

**来源 PRD**：{路径}
**所选里程碑**：{里程碑或阶段名称}
**复杂度**：{Small | Medium | Large}

## 摘要
{2-3 句话}

## 需借鉴的模式
| 类别 | 来源 | 模式 |
|---|---|---|
| 命名 | `path:line` | {简短描述} |
| 错误 | `path:line` | {简短描述} |
| 测试 | `path:line` | {简短描述} |

## 需变更的文件
| 文件 | 操作 | 原因 |
|---|---|---|
| `path` | CREATE / UPDATE / DELETE | {原因} |

## 任务
### 任务 1：{名称}
- **操作**：{做什么}
- **借鉴**：{要遵循的模式}
- **验证**：{证明正确性的命令}

## 验证
```bash
{项目特定的验证命令}
```

## 风险
| 风险 | 可能性 | 缓解措施 |
| --- | --- | --- |

## 接受
- [ ] 所有任务已完成
- [ ] 验证通过
- [ ] 模式得到借鉴，而非重新发明

````

写入 artifact 后，报告其路径并等待确认，然后才能编写代码。

## 示例用法

```markdown
用户：/plan 我需要在市场结算时添加实时通知

AI：
# 实施计划：实时市场结算通知

## 需求重申
- 当用户关注的市场结算时，向其发送通知
- 支持多种通知渠道（应用内、邮件、webhook）
- 确保通知可靠送达
- 包含市场结果和用户持仓结果

## 实施阶段

### 阶段 1：数据库 Schema
- 添加 notifications 表，列：id、user_id、market_id、type、status、created_at
- 添加 user_notification_preferences 表，用于渠道偏好设置
- 在 user_id 和 market_id 上创建索引以提升性能

### 阶段 2：通知服务
- 在 lib/notifications.ts 中创建通知服务
- 使用 BullMQ/Redis 实现通知队列
- 为送达失败的投递添加重试逻辑
- 创建通知模板

### 阶段 3：集成点
- 接入市场结算逻辑（当状态变为“已结算”时触发）
- 查询所有在该市场中持有头寸的用户
- 为每个用户将通知加入队列

### 阶段 4：前端组件
- 在 header 中创建 NotificationBell 组件
- 添加 NotificationList 模态框
- 通过 Supabase 订阅实现实时更新
- 添加通知偏好设置页面

## 依赖项
- Redis（用于队列）
- 邮件服务（SendGrid/Resend）
- Supabase 实时订阅

## 风险
- 高：邮件到达率（需配置 SPF/DKIM）
- 中：单个市场有 1000+ 用户时的性能
- 中：市场频繁结算时可能造成通知轰炸
- 低：实时订阅开销

## 预估复杂度：MEDIUM
- 后端：4-6 小时
- 前端：3-4 小时
- 测试：2-3 小时
- 总计：9-13 小时

**等待确认**：是否按此计划进行？（是/否/修改）
```

## 重要提示

**关键**：在你明确用“是”、“继续”或类似的肯定性回复确认之前，该命令**不会**编写任何代码。

如果你想修改，请回复：
- “修改：[你的修改内容]”
- “不同方案：[替代方案]”
- “跳过阶段2，先做阶段3”

## 与其他命令的衔接

制定计划之后：
- 使用 `tdd-workflow` skill 以测试驱动开发方式进行实施
- 如果出现构建错误，使用 `/build-fix`
- 使用 `/code-review` 评审已完成的实现
- 使用 `/pr` 或 `/prp-pr` 发起 Pull Request

> **需要先明确需求？** 使用 `/plan-prd` 在 `.claude/prds/{name}.prd.md` 生成一份精简 PRD。
>
> **需要旧版 PRP 流程？** 使用 `/prp-plan` 进行深度 PRP 规划并生成 `docs/PRPs/` artifact。使用 `/prp-implement` 以严格的验证循环执行这些计划。

## 可选 Planner Agent

ECC 还为手动安装场景（含 agent 文件）提供了一个 `planner` agent。仅当本地运行时环境已暴露该 subagent 且用户明确要求你委托规划任务时才使用它。

如果 `planner` subagent 不可用，则继续以内联方式规划，而不是显示“Agent type 'planner' not found”错误。

对于手动安装，源文件位于：`agents/planner.md`
