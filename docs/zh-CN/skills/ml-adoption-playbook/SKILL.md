# ML 落地指南（Playbook）

本 skill 提供了一套自适应方法论，用于将 machine learning 模型集成到现有软件工程项目中。它通过结构化 ML 应如何被研究、解耦、训练和集成，弥合了传统 SWE 与 MLOps 之间的鸿沟。

## 何时启用

- 用户要求向其现有代码库"添加 ML"或"添加算法"。
- 规划将新模型（例如推荐、分类、预测）集成到非 ML 应用中。
- 为 agent 结构化一套自适应地构建、训练和部署 ML 组件的工作流。

## 第一阶段：问题定义与可行性评估

在编写模型代码之前，先确立"为什么"和"怎么做"。
- **Heuristic 检查：** 询问用户一个简单的 heuristic（例如 regex、基于规则的排序）是否能更快地解决问题。如果能，从那里开始。
- **指标定义：** 定义 ML 模型试图改善的业务指标（例如点击率、降低延迟）。
- **错误预算：** 定义"糟糕"的预测是什么样子，以及系统应如何处理它。

## 第二阶段：数据准备度

没有干净、可访问的数据，ML 毫无用处。
- **审查数据源：** 确定训练数据存放在哪里。是实时数据库、静态 CSV，还是 API？
- **数据契约：** 为输入数据建立 schema。需要哪些特征？如果某个特征缺失会发生什么？
- **防泄漏：** 确保用户提议的数据划分不会意外地将未来信息泄漏到训练集中（例如，对时间序列数据进行时间顺序划分）。

## 第三阶段：架构集成与解耦

不要将模型推理与核心业务逻辑紧密耦合。
- **API 边界：** 建议将模型置于 API endpoint 之后（例如使用 `fastapi-patterns` 或 `django-patterns`），或置于一个专用的服务类之后。
- **回退机制：** 设计默认状态。如果模型响应时间过长或抛出错误，系统必须优雅地回退到硬编码规则。
- **Feature Flags：** 用 feature flag 包裹新的 ML 推理调用，使其可以安全地推出（或回滚）。

## 第四阶段：模型实现与训练

为可复现性和迭代性组织代码结构。
- **从简单开始：** 先构建一个基线模型（例如简单的 scikit-learn Logistic Regression 或一个最基础的 PyTorch 线性层）。
- **可复现性：** 应用 `pytorch-patterns` 或类似最佳实践：固定随机种子、使代码设备无关，并明确记录 tensor/array 形状。
- **自动化证据：** 要求数据转换和推理 schema 有测试覆盖。不接受没有评估脚本将其与基线进行对比的模型。

## 第五阶段：交接至 MLOps

一旦基线模型集成完成，将重点转向持续运维。
- **参考 `mle-workflow`：** 引导用户建立实验跟踪、模型注册表和漂移检测。
- **CI/CD：** 将模型评估步骤添加到现有 CI pipeline 中，以确保未来的 commit 不会降低模型性能。

## 迭代式 Agent 工作流

通过本指南协助用户时，agent 应当：
1. **提出澄清性问题**，以在提出架构之前完成第一阶段。
2. **起草数据契约**，在第二阶段供用户审批。
3. **编写解耦接口**（API/Service），在第三阶段*先于*编写训练循环。
4. **交付可复现脚本**，在第四阶段该脚本训练模型并保存 artifact。
