# Claude Code 三组件对比：agents / commands / skills

> Claude Code 有三类用户可配置组件——**commands**（斜杠命令）、**skills**（技能）、**agents**（子代理）。ECC 这套插件同时大量使用了三者（~150 commands、277 skills、67 agents）。本文从**原理机制、使用方法、最佳场景、优势、缺点**等维度横向对比，帮你判断什么时候用哪个。
>
> 所有结论基于官方文档（`code.claude.com/docs/en/{skills, sub-agents, agent-sdk/slash-commands}`）+ ECC 仓库实例 + 前几轮动态实证（adapter 输出、dry-run）。

---

## 1. 一句话定位

| 组件 | 一句话 | 运行在哪 |
|---|---|---|
| **command** | 预制 prompt 模板，`/xxx` 触发后注入对话 | 主对话 |
| **skill** | 可复用知识包（SKILL.md + 配套文件），按场景自动或手动触发 | 主对话 |
| **agent** | 独立 AI worker，有自己的脑子、工具、模型，干完只汇报结论 | **隔离 context** |

**最本质区别**：command / skill 都"在主对话里注入指令"，agent 是"派一个分身去独立 context 干活，只把结论带回来"。

| **ECC 插件安装后** | ✅（`/ecc:xxx`） | ✅（`ecc:xxx` 命名空间） | ✅ |

## 3. 分维度详述

### 3.1 原理 / 机制

#### commands — 预制 prompt 的"模板引擎"
- **发现**：Claude Code 扫描 `~/.claude/commands/*.md` 和 `.claude/commands/*.md`，**只看一层**，命令名 = 文件名去 `.md`（[plan.md](../commands/plan.md) → `/plan`）。frontmatter 的 `name` 字段不影响命令名。
- **执行流水线**（用户输入 `/xxx 参数` 后）：
  1. 匹配 `<name>.md`
  2. **预处理**（送给 Claude 之前）：行首 `` !`cmd` `` 或 ```` ```! ```` 块 → 本地执行、输出替换进正文；`@<路径>` → 文件内容内联
  3. **变量替换**：`$ARGUMENTS` → 全部参数；`$1`/`$ARGUMENTS[0]` → 第 N 个；正文没 `$ARGUMENTS` 则追加 `ARGUMENTS: ...`
  4. 渲染后的正文（frontmatter 之后）作为**单条 user 消息**注入对话（不是 system prompt）
  5. Claude 按正文指令自主循环

> 注意：普通三反引号 ```` ```bash ```` 代码块**不会被执行**，只是给 Claude 看的指令文本；Claude 收到后自己用 Bash 工具跑。

#### skills — 可复用的"知识注入"
- **发现**：扫描 `~/.claude/skills/<name>/SKILL.md`，**只看一层**（不递归），触发名 = **目录名**。frontmatter `name` 仅作显示标签。
- **触发**：① Claude 按 `description` 自动判断相关性加载（概率性）；② 用户 `/目录名` 显式触发。
- **运行**：渲染后的 SKILL.md 内容作为消息注入并**留存主对话整个 session**。支持配套文件（模板、脚本、reference md），是 skill 相对 command 的主要形态优势。

#### agents — 隔离 context 的"分身"
- **发现**：扫描 `~/.claude/agents/*.md`，**递归扫描**（可分子目录组织）。agent 身份 = **frontmatter `name` 字段**，**文件名无关**。session 启动时加载，磁盘改动需重启 session。
- **运行**：每个 subagent 跑在**独立 context 窗口**，看不到主对话历史。主 Claude 写一条"委派消息"总结任务传给它；它用自己的 system prompt（agent 文件正文）+ 委派消息 + CLAUDE.md 启动，自主循环后只把 **summary** 回传主对话，中间 verbose 输出留在自己的 context。
- **底层工具**：主 Claude 通过 **Agent 工具**调用 subagent（v2.1.63 前叫 Task 工具，旧名兼容）。

> **关键对比**：同样是"注入指令"，command/skill 进主对话（占 context、可见历史），agent 隔离运行（省 context、无历史）。这是选 agent 还是 skill/command 的核心权衡。

### 3.2 使用方法

#### commands
```yaml
---
description: Restate requirements, assess risks, create step-by-step plan.
argument-hint: "[feature description | path/to/*.prd.md]"
disable-model-invocation: true   # 可选：禁止自动触发，只能手动 /xxx
allowed-tools: Read, Grep, Glob    # 可选：激活期间免授权工具
model: opus                        # 可选：本次用 opus
---
正文：给 Claude 的指令模板，可用 $ARGUMENTS / $1 / !`cmd` / @path
```
调用：`/plan 添加用户认证`。ECC 实例：[plan.md](../commands/plan.md)、[code-review.md](../commands/code-review.md)。

#### skills
```yaml
---
name: tdd-workflow
description: Use this skill when writing new features, fixing bugs, or refactoring...
disable-model-invocation: false    # 可选：true 则只能手动 /xxx
user-invocable: true               # 可选：false 则不进 / 菜单（仅自动）
---
```
目录结构：`skills/tdd-workflow/SKILL.md` + 可选 `templates/`、`scripts/`、`references/`。
调用：自动触发（Claude 按 description 判断）或 `/tdd-workflow`。ECC 实例：[tdd-workflow](../skills/tdd-workflow/SKILL.md)、[security-review](../skills/security-review/SKILL.md)。

#### agents
```yaml
---
name: code-reviewer
description: Expert code review specialist. Proactively reviews code for quality, security...
tools: ["Read", "Grep", "Glob", "Bash"]   # 白名单：只能用这些
model: sonnet                              # 用 sonnet（主对话可能用 opus）
---
正文：该 agent 的角色 system prompt
```
调用（**没有 `/agent:name` 斜杠命令**）：
- **自动委派**：Claude 按 `description` 自行决定
- **自然语言**："用 code-reviewer agent 审查这段代码"（Claude 仍可拒绝）
- **@-mention**：`@"code-reviewer (agent)"`（**保证触发**）
- **整会话**：`claude --agent code-reviewer` 或 settings `"agent": "code-reviewer"`

ECC 的 agent 设计（实测）用 `tools` + `model` 做**最小权限 + 成本分工**：

| agent | tools | model | 设计意图 |
|---|---|---|---|
| [planner](../agents/planner.md)、[architect](../agents/architect.md) | `Read,Grep,Glob`（只读） | **opus** | 深度思考：强模型 + 禁止改代码 |
| [code-reviewer](../agents/code-reviewer.md) | `Read,Grep,Glob,Bash` | sonnet | 审查：能跑命令验证，不动文件 |
| build-error-resolver | `Read,Write,Edit,Bash,Grep,Glob`（可写） | sonnet | 执行：允许改代码修构建 |

### 3.3 最佳使用场景

| 场景信号 | 选谁 |
|---|---|
| 固定流程入口、必须每次触发（如 `/plan`、`/deploy`） | **command** |
| 需要 `!` 预处理先跑命令拿数据再交给 Claude | **command** |
| 参数化指令（`$ARGUMENTS` 切模式） | **command** |
| 可复用的方法论 / 领域知识（TDD 步骤、安全清单、React 模式） | **skill** |
| 需要配套模板/脚本（如 PRD 模板、代码生成脚手架） | **skill** |
| 希望 Claude 按场景**自动**激活（不用记命令名） | **skill** |
| 输出冗长但你只要结论（全量代码审查、大规模搜索、深度调研） | **agent** |
| 要隔离 context、避免 verbose 污染主对话 | **agent** |
| 要限定工具权限（最小权限）或换模型（opus 思考、sonnet 执行） | **agent** |
| 多个独立子任务可并行 | **agent**（多个并行） |

### 3.4 优势

**commands**
- ✅ 触发**确定性强**：`/xxx` 必触发，不靠概率匹配
- ✅ 轻量：单文件、无目录开销
- ✅ 参数灵活：`$ARGUMENTS` / `$1` / `!` 展开 / `@` 引用
- ✅ 入口清晰：用户主动调用，可控

**skills**
- ✅ 可**自动触发**：按 description 匹配场景，用户不用记命令
- ✅ 支持配套文件（模板、脚本、reference），承载复杂方法论
- ✅ 官方未来方向："Custom commands have been merged into skills"
- ✅ 命名空间隔离（plugin 形态）

**agents**
- ✅ **省 context**：只回 summary，verbose 留在隔离 context（核心价值）
- ✅ **最小权限**：`tools` 白名单限制爆炸半径
- ✅ **模型分工**：opus 做规划、sonnet 做执行，成本/能力最优
- ✅ 可并行多个 agent 同时干活
- ✅ 失败隔离：subagent 出错不直接污染主对话

### 3.5 缺点

**commands**
- ❌ 占主对话 context（指令和后续输出都留在主对话）
- ❌ 不能自动触发（必须用户 `/xxx`，除非理解成 skill）
- ❌ 无配套文件（复杂逻辑难承载）

**skills**
- ❌ 触发**概率性**：依赖 description 匹配质量，可能该触发没触发、不该触发误触
- ❌ 占主对话 context（SKILL.md 渲染后留存整个 session）
- ⚠️ **ECC 手动安装的坑**：`install.sh` 把 skill 放到 `~/.claude/skills/ecc/<name>/`，多一层 `ecc/` → Claude Code 只扫一层 → **全部失效**（见第 6 节）

**agents**
- ❌ 启动开销大：每次委派要起新 context、写委派消息
- ❌ **看不到主对话历史**：只收到委派消息，质量依赖主 Claude 总结得准不准
- ❌ 不可交互：没有 `AskUserQuestion`、`EnterPlanMode` 等工具，遇决策只能凭指令猜
- ⚠️ 同 scope 内 frontmatter `name` 重复会被**静默丢弃**（官方："keeps one and discards the other without warning"）
- ⚠️ 加载时机：改盘后需重启 session 才生效

## 4. 选择决策树

```
你要解决的问题是什么？
│
├─ 想要一个"固定入口"，每次必触发，传参数跑流程
│   → command（/xxx）
│
├─ 想要"可复用知识"，让 Claude 在合适场景自动用上
│   → skill（按 description 自动 / 目录名显式）
│
└─ 想让"独立分身"去干冗长的活，只回结论，不污染主对话
    → agent（自动委派 / @mention / --agent）
```

**补充判断**：
- 任务**输出冗长**且你只要结论 → agent
- 任务需要**限定工具**（防止改代码）→ agent（tools 白名单）
- 任务需要**换模型**（深度思考用 opus）→ agent（model 字段）
- 任务就是**一段固定指令** → command
- 任务是**一套方法论/知识**，反复用 → skill

## 5. 三者协作（ECC 的典型编排）

三者不是互斥，ECC 经常组合用。典型链路（来自 ECC 工作流）：

```
/plan "添加用户认证"              ← command（入口，必触发）
    ↓ 正文指令："分析需求并制定计划"
主 Claude 委派 planner agent      ← agent（深度思考，opus + 只读）
    ↓ planner 用 search-first skill  ← skill（调研方法论）
    ↓ 产出 Implementation Plan
主 Claude 委派 architect agent    ← agent（架构决策）
    ↓ 产出设计
/tdd-workflow                     ← skill/command（RED→GREEN→REFACTOR）
    ↓ 写代码
主 Claude 委派 code-reviewer agent ← agent（审查，sonnet）
    ↓ 审查 summary 回主对话
```

**常见组合模式**：
- **command 当入口、skill 当知识库**：command 正文常写 "Use the xxx skill"。命令保证触发，skill 提供详细方法论。
- **command 间接触发 agent**：command 正文指示 Claude "delegate to xxx agent"。
- **agent 预加载 skill**：agent frontmatter 的 `skills` 字段可预加载某些 skill 全文到 subagent context。

> ⚠️ **手动安装下的连锁问题**：command/agent 正文里引用 skill 时，若 skill 在 `~/.claude/skills/ecc/`（手动安装默认位置），skill 不被识别 → 引用落空。详见第 6 节。

## 6. ECC 手动安装 vs 插件安装下的差异

这是 ECC 用户最实际的关心点。同一套组件，两种安装方式下可用性不同：

| 组件 | 手动安装（`install.sh --profile full`） | 插件安装（`/plugin install ecc@ecc`） |
|---|---|---|
| **commands** | `~/.claude/commands/*.md`（扁平）→ ✅ 可用 | plugin 命名空间 `/ecc:xxx` → ✅ |
| **agents** | `~/.claude/agents/*.md`（扁平，递归扫）→ ✅ 可用 | ✅ |
| **skills** | `~/.claude/skills/ecc/<name>/`（嵌套）→ ❌ **失效** | plugin `skills/ecc/<name>/` → ✅（`ecc:xxx` 命名空间） |
| **rules** | `~/.claude/rules/ecc/` → ✅（Claude Code 读 rules） | ❌ 插件不支持分发 rules |

**为什么只有 skills 在手动安装下失效？**

`install.sh` 的 claude-home adapter（[claude-home.js:29-40](../scripts/lib/install-targets/claude-home.js#L29)）把 `skills/*` 和 `rules/*` 重映射进 `ecc/` 子目录（路径隔离设计），其余组件（agents/commands/hooks）扁平放。但 Claude Code 对 skills 只扫一层（`~/.claude/skills/<name>/`），所以 `skills/ecc/` 这层让 skills 全部不被识别。agents 反而没事，因为它**递归扫描**。commands 也没事，因为它扁平放。

官方明确警告（[README.md:974](../README.md#L974)）："Do not nest manual installs under ~/.claude/skills/ecc/"。

**手动安装的正确做法**：
- 想用 ECC skill：扁平复制 `cp -r skills/<name> ~/.claude/skills/`，或用 `configure-ecc` 向导
- 想省事且要 skill：直接用插件方式 `/plugin install ecc@ecc`

详见 [安装过程分析.md](安装过程分析.md) 和 [初级使用指南.md](初级使用指南.md)。

## 7. 端到端示例：一次 `/code-review` 的完整生命周期

```
1. 用户输入：/code-review 123
2. Claude Code 匹配 ~/.claude/commands/code-review.md
3. 预处理：
   - $ARGUMENTS → "123"
   - 正文里若有 !`git diff` → 本地执行，输出替换进 prompt
4. 渲染后的命令正文作为【单条 user 消息】注入主对话
   （内容含："若 $ARGUMENTS 含 PR 号 → PR Review Mode"）
5. 主 Claude 读到指令，决定委派 code-reviewer agent
   → 用 Agent 工具，写委派消息："审查 PR #123 的质量/安全"
6. code-reviewer subagent 启动（独立 context）：
   - system prompt = agents/code-reviewer.md 正文
   - tools = [Read, Grep, Glob, Bash]
   - model = sonnet
   - 看不到主对话历史，只看到委派消息
7. subagent 自主循环：gh pr diff 123 → Read 改动文件 → Grep 找问题 → 写审查笔记
8. subagent 完成：把审查结论作为 summary 回传主对话
   （中间的 diff 输出、grep 结果都留在 subagent context，不污染主对话）
9. 主 Claude 收到 summary，向用户呈现审查结果
```

**这个例子里三者各司其职**：
- **command**（code-review.md）：提供"如何审查"的流程入口和参数解析
- **agent**（code-reviewer）：在隔离 context 里跑冗长的 diff/grep，只回结论
- **skill**（如 security-review）：若 agent 或 command 引用，提供安全检查清单知识（前提是 skill 被正确识别）

## 8. 案例剖析：同名双轨 — `/plan`（command）与 `planner`（agent）

ECC 同时提供了 [commands/plan.md](../commands/plan.md)（slash command）和 [agents/planner.md](../agents/planner.md)（subagent），两者都做"实现规划"。这是理解 command 与 agent 差异的绝佳样本。

### 8.1 核心关系：同名双轨、独立可替代

两者**不是**"命令调用 agent"的上下游，而是**两条平行的 planning 路径**：

- `/plan`（command）是主入口，默认**内联运行**，自包含完整工作流
- `planner`（agent）是**可选增强**，仅在 agent 已加载**且**用户明确要求委派时才用

### 8.2 plan.md 自己的界定（原文）

[plan.md:10](../commands/plan.md#L10) 开篇即声明默认不调 subagent：

> Run inline by default. **Do not call the Task tool or any subagent by default.** This keeps `/plan` usable from plugin installs that ship commands without agent files.

[plan.md:193-200](../commands/plan.md#L193) 末尾"Optional Planner Agent"给出使用 agent 的两个**同时**条件：

> Use it only when the local runtime already exposes that subagent **and** the user explicitly asks you to delegate planning.

即：`/plan` 永远走 command 内联；想用 agent 必须用户**另行明确点名**。

### 8.3 两者对比

| 维度 | `/plan`（command） | `planner`（agent） |
|---|---|---|
| 触发 | `/plan [参数]` | 自动委派 / 用户明确点名（**不是** `/plan` 触发） |
| 运行 | 主对话内联 | 独立隔离 context |
| 模型 | 继承主对话 | **opus** |
| 工具 | 主对话全部工具 | `Read,Grep,Glob`（**只读**） |
| 参数 | `$ARGUMENTS`（PRD 路径 / 自由文本 / 空） | 靠委派消息传任务 |
| 内容侧重 | **工程流程**：输入模式、Pattern Grounding（搜代码库约定）、PRD artifact 输出、与 `/tdd-workflow`/`/code-review` 集成、等确认门禁 | **思维方法**：规划方法论（4 步）、计划格式模板、Stripe 完整示例、sizing/phasing、red flags 检查清单 |
| 写 artifact | ✅ 可写 `.claude/plans/{name}.plan.md` | ❌ 只回 summary |
| 交互 | ✅ 能等用户确认（`WAIT for CONFIRM`） | ❌ subagent 无 `AskUserQuestion` |
| 依赖 | **不依赖** agent（缺失则内联，不报错） | 独立存在，可被主 Claude 直接委派 |

### 8.4 为什么双轨（互补设计）

针对 command 与 agent 各自短板的互补：

| 考量 | command 路径 | agent 路径 |
|---|---|---|
| 兼容性 | ✅ 插件不发 agent 文件也能用（L10 的明确动机） | ⚠️ 依赖运行时已加载该 agent |
| 可见性 | ✅ 在主对话内，看得见完整历史 | ❌ 隔离 context，只收委派消息 |
| context 成本 | ❌ 规划过程占主对话 | ✅ 只回 summary，省 token |
| 思考深度 | 继承主对话模型 | ✅ opus + 专注方法论 |
| 改代码防护 | 软门禁（"WAIT for CONFIRM"） | ✅ 硬限制（工具白名单无 `Write`/`Edit`） |
| 中途交互 | ✅ 能等用户确认 | ❌ 不能 |

### 8.5 与典型"command→agent"模式的差异

第 5 节描述的典型协作是"command 当入口、指示 Claude 调 agent 干活"。但 `plan` ↔ `planner` 是**反例变体**：

```
典型：  /xxx ──(command 正文指示 delegate)──> agent 干活
这里：  /plan ──(默认内联，明确禁止调 agent)──> command 自己干
        "用 planner agent 规划" ──(用户另行点名)──> agent 独立干
```

设计动机（[plan.md:10](../commands/plan.md#L10)）：保证 command 在**最小安装**（只发 command 文件、不发 agent 文件）下也能跑。agent 是"有就更深度"的增强，不是 command 的依赖。

### 8.6 一致性与差异

- **一致性**：两者都坚守"规划阶段不写代码"——command 靠"WAIT for CONFIRM"门禁（[plan.md:17](../commands/plan.md#L17)），agent 靠 `tools:["Read","Grep","Glob"]` 工具白名单（[planner.md:4](../agents/planner.md#L4)）。
- **差异**：agent 的限制是**硬**的（subagent 想写也写不了），command 的限制是**软**的（靠指令遵守）。这正体现了 agent"最小权限"的设计优势。

> **结论**：这是"按运行形态选组件"的教科书式案例——同一能力（planning）如何分别用 command（主对话、兼容、可交互）和 agent（隔离、深度、硬权限）实现，以及为什么 command 要故意不绑定 agent。
