> 属于 PRP 工作流系列的一部分。

# PRP 计划

创建一个详细的、独立的实现计划，其中包含实现某个功能所需的所有代码库模式、约定和上下文，以便一次性完成。

**核心理念**：一个优秀的计划包含了实施所需的一切，无需再问任何问题。每一种模式、每一种惯例、每一个 gotcha —— 一次性捕获并记录下来，贯穿始终。

**黄金法则**：在实施过程中如果需要搜索代码库，现在就把这些知识捕获到计划中。

---

## 阶段 0 — DETECT

根据 `$ARGUMENTS` 判断输入类型：

| 输入模式 | 判定 | 动作 |
|---|---|---|
| 以 `.prd.md` 结尾的路径 | 指向 PRD 的文件路径 | 分析 PRD，找到下一个 `待开始` 的阶段 |
| 包含“实施阶段”的 .md 文件路径 | 类 PRD 的文件 | 分析各阶段，找到下一个 `待开始` 的阶段 |
| 指向其他任意文件的路径 | 参考文件 | 读取文件获取上下文，按 自由文本 处理 |
| 自由文本 | 功能描述 | 直接进入阶段 1 |
| 为空 / 空白 | 无输入 | 询问用户要规划什么功能 |

### PRD 解析（当输入为 PRD 时）

1. 使用 `cat "$PRD_PATH"` 读取 PRD 文件
2. 解析 **实施阶段** 章节
3. 按状态查找各阶段：
   - 查找 `待开始` 阶段
   - 检查依赖链（某个阶段可能依赖于前序阶段处于 `已完成` 状态）
   - 选择**下一个符合条件的 待开始 阶段**
4. 从所选阶段中提取：
   - 阶段名称和描述
   - 验收标准
   - 对前序阶段的依赖
   - 任何范围说明或约束
5. 将该阶段的描述作为要规划的功能

如果没有剩余的 待开始 阶段，报告所有阶段均已完成。

## 阶段 1 — 解析

提取并明确功能需求。

### 功能理解

根据输入内容（PRD 阶段或自由形式描述），确定：

- 正在建设的**内容** （具体交付成果）
- **为什么**这很重要（用户价值）
- **谁**使用它（目标用户/系统）
- 它应该放在**哪里** （代码库的哪一部分）

### 用户故事

格式如下：
```
作为[用户类型]，
我想要[能力]，
这样就有了[好处]。
```

### 复杂度评估

| 等级 | 指标 | 典型范围 |
|---|---|---|
| **Small** | 单个文件、独立改动、无新依赖 | 1-3 个文件，<100 行 |
| **Medium** | 多文件、沿用现有模式、少量新概念 | 3-10 个文件，100-500 行 |
| **Large** | 跨领域问题、新模式、外部集成 | 10+ 个文件，500+ 行 |
| **XL** | 架构级变更、新子系统、需要迁移 | 20+ 个文件，考虑拆分 |

### 歧义门

如果其中任何一项不清楚， 请**停止操作并询问用户**后再继续：

- 核心交付物模糊
- 成功标准未定义
- 存在多种合理解读
- 技术方案存在诸多未知因素

不要猜测，要提问。基于假设制定的计划在执行过程中注定失败。

## 阶段 2 — 探索

深入挖掘代码库信息。直接在代码库中搜索以下每个类别。

### 代码库搜索（8 个类别）

针对每个类别，使用 grep、find 和文件读取进行搜索：

1. **相似实现** —— 寻找与计划功能相似的现有功能。寻找类似的模式、端点、组件或模块

2. **命名约定** —— 明确代码库相关区域中文件、函数、变量、类和 export 的命名方式。

3. **错误处理** —— 了解在类似的代码路径中，错误是如何被捕获、传播、记录和返回给用户的。

4. **日志模式** —— 确定日志打印什么内容、哪个级别以及日志的格式。

5. **类型定义** —— 找到相关的 type、interface、schema 及其组织方式。

6. **测试模式** —— 了解相似功能的测试方式。注意测试文件的位置、命名、设置/清理模式和断言风格。

7. **配置** —— 查找相关的配置文件、环境变量和功能标志。

8. **依赖** —— 识别相似功能使用的 package、imports、internal modules。

### 代码库分析（5 条追踪路径）

读取相关文件进行跟踪：

1. **入口点** —— 请求/操作如何进入系统并到达您正在修改的区域？
2. **数据流** —— 数据如何在相关的代码路径中流动？
3. **状态变更** —— 哪些状态被修改、在哪里修改？
4. **契约** —— 必须遵守哪些 interface、API 或协议？
5. **模式** —— 使用了哪些架构模式（repository、service、controller 等）？

### 统一发现表

将结果汇编成一份参考文献：

| 类别 | 文件:行号 | 模式 | 关键片段 |
|---|---|---|---|
| 命名 | `src/services/userService.ts:1-5` | camelCase service、PascalCase type | `export class UserService` |
| 错误 | `src/middleware/errorHandler.ts:10-25` | 自定义 AppError class | `throw new AppError(...)` |
| ... | ... | ... | ... |

## 阶段 3 — 研究

如果该功能涉及外部库、API 或不熟悉的技术：

1. 搜索网络查找官方文档
2. 查找使用示例和最佳实践
3. 识别指定版本的 gotchas

将每项发现按以下格式列出：

```
关键洞察：[你学到了什么]
适用范围：[此条款影响计划的哪一部分]
GOTCHA：[所有警告或指定版本的 issues]
```

如果该功能仅使用已充分理解的内部模式，跳过本阶段并注明："无需外部研究——该功能使用已建立的内部模式。"

## 阶段 5 — 建筑师

### 策略设计

定义实现方案：

- **方案**：方法 ：高层策略（例如，“按照现有存储模式添加新的服务层”）
- **备选方案**：还评估了哪些其他方案？为什么这些方案被否决了？
- **范围**：明确界定将要构建的内容边界
- **不构建的内容**：不构建 ：明确列出超出范围的内容（防止实施过程中范围蔓延）

## 测试策略

### 单元测试

对每行测试标注“先行验证”（test-first）。判定规则：

- **是**：高逻辑密度行为——算法、解析、计价、状态转换、边界条件丰富的纯逻辑。此类测试必须在实现之前编写并确认失败（red 证明）
- **否**：CRUD、UI、配置、胶水代码。实现后按常规流程编写测试
- 不允许留空——每行必须有明确标注

| 测试 | 输入 | 预期输出 | Edge Case？ | 先行验证 |
|---|---|---|---|---|
| ... | ... | ... | ... | 是/否 |

### 集成测试

**豁免判定**（默认关闭；仅限以下类别，须注明理由——豁免改变验证形态，不免除验证）：
- [ ] 豁免 —— 类别：[无运行时行为的变更（纯文档/配置/静态资源）| 自动化基建缺失]，理由：[……]，并将集成验证降级写入「手动验证」清单

未声明豁免时，定义本次需要**新增**的集成测试，以及因接缝变更须**调整/删除**的既有集成测试：

| 动作 | 场景 | 涉及接缝 | 测试文件 | 操作/请求 | 预期结果 |
|---|---|---|---|---|---|
| 新增/调整/删除 | ... | 模块×数据库 | `tests/integration/xxx.spec.ts` | ... | ... |

- 若本次变更既无新增集成场景、也不影响既有用例，注明“无变化——复用既有集成测试”；此时「验证命令 → 集成测试」仍照常填写命令，执行时运行既有用例以防接缝回归
- 「测试文件」按项目既有集成测试的位置与命名约定填写，且须在「验证命令 → 集成测试」命令的收集范围内（如 jest testMatch / pytest 收集规则）；调整/删除行的「测试文件」列须指向既有用例所在文件（规划时已通过接缝关键词——路由路径/函数名/表名——定位，实施时直接按此列取文件）
